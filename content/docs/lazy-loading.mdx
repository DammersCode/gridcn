`useDataGridServerRows({ mode: "scroll" })` fetches the rows the grid scrolls into. You give it a
`fetchRows({ start, end, signal, spec })` function that answers with the rows and the row count.

<ComponentPreview name="data-grid-lazy-demo" />

<InstallCommand item="data-grid-server" manual manualSlot={<ManualInstall item="data-grid-server" />} />

Scroll mode gives one continuous scrollable surface: no page boundary, a grid that fills in as the
user scrolls. It fits one continuous dataset best. Explicit, bookmarkable pages with a bounded
per-request payload are [Pagination](/docs/pagination). Virtualization renders huge datasets cheaply
either way. Neither exists for rendering performance. Using scroll mode and pagination on one grid is not supported.

<Callout type="idea" title="loading vs. scroll mode">
  The `loading` prop of the core (see [Styling & theming](/docs/styling-theming#loading-state))
  is a whole-grid flag with one skeleton look, for an ordinary fully-controlled fetch, with no
  per-row granularity and no partial data. Use scroll mode when individual row *blocks* load
  independently as the user scrolls. Its skeleton cells are per-row, not grid-wide.

  `server.rootProps` carries `loading`, `error`, and `onRetry`. `loading` is `true` while any block
  request is in flight and shows the slim progress bar under the header. The unloaded rows keep
  their skeleton cells.
</Callout>

Every unloaded-row skeleton cell carries `data-skeleton` (see
[Data-attribute contract](/docs/styling-theming#data-attribute-contract)), for restyling the
shimmer with plain CSS instead of a class override.

## Usage

<NewBadge />

```tsx
"use client";

import { DataGrid } from "@/components/data-grid/data-grid";
import { useDataGridServerRows } from "@/components/data-grid-server/data-grid-server";

function OrdersGrid() {
  const server = useDataGridServerRows<Order>({
    mode: "scroll",
    getRowId: (row) => row.id,
    fetchRows: async ({ spec, start, end, signal }) => {
      const answer = await api.orders({ ...spec, offset: start, limit: end - start, signal });
      return { rows: answer.rows, totalRowCount: answer.total };
    },
  });

  return <DataGrid {...server.gridProps} columns={columns} />;
}
```

The first request is always block 0: rows `[0, blockSize)`. The first answer picks the fetch order. An
answer with `totalRowCount` and no `nextCursor` gives random access. The hook sizes `data` to that
count, and every row without data renders as a skeleton. When the rendered rows move, the hook
rounds them plus `overscan` out to `blockSize` blocks and fetches each gap, one request per block.

A request holds `{ spec, start, end, cursor, signal }`. `cursor` is `undefined` in random access.
`signal` aborts when a spec change, a count change, or an unmount replaces the request.

For a composed layout, spread `server.providerProps` onto `DataGridProvider` and `server.rootProps` onto
`DataGridRoot`. `server.gridProps` is both parts together.

<ComponentPreview name="data-grid-server-side-demo" />

| Option | Default | What it does |
|---|---|---|
| `mode` | `"pages"` | `"scroll"` fetches fixed-size blocks as the rendered rows move. |
| `blockSize` | 50 | Rows per request. Requests align to multiples of it. |
| `overscan` | 30 | Rows fetched beyond the rendered rows on each side. |
| `spec`, `defaultSpec`, `onSpecChange` | `{}` | Controls or seeds the sort, filter, and search text. |
| `onLoaded` | none | Fires after a block lands, with the range it covers. |
| `onError` | none | Fires after a request fails. |
| `onDataChange` | none | Fires after the hook merged an edit, insert, or delete. |

A server page that you cache by its own size does not split cleanly when `blockSize` differs from it.
Set `blockSize` to that page size to keep one cache entry per request.

The hook reads the row count from the first answer, so the grid needs no separate count endpoint.
If your backend counts with a separate call, make that call inside `fetchRows` and return both.

Behavior the grid applies by itself:

- `data` is a sparse array with the length of the count. Loaded indices hold real rows.
  Unloaded indices are holes (`undefined`), which the core renders as skeleton cells.
- Function-form row and cell callbacks are skipped on holes. `readOnly(row)`,
  `getRowClassName`, and the function forms of `getCellClassName` / `column.cellClassName`
  never receive an `undefined` row. The skeleton row is inert.
- Placeholder row ids are index-derived for unloaded rows (`getRowId` only runs on rows
  that exist). This id is unstable. It does not survive a block being unloaded and reloaded
  with different content at the same index, but this is fine. An unloaded row carries no
  selection, edit, or scroll-anchor state worth preserving across that transition.
- Already-loaded and in-flight blocks are never requested again. A window that partly overlaps
  what is loaded fetches the remaining blocks only. Adjacent loaded blocks merge, so later gap
  calculations see one covered span.
- A changed `totalRowCount` in any answer starts the blocks over, like a spec change.
- A spec change aborts every request, drops the loaded rows, and fetches block 0 again.
- The hook writes the blocks that land in one frame with one update of `data`.
- Requests abort on unmount, through the `AbortSignal` passed to `fetchRows`.
- A block that fails stays unloaded and never counts as loaded. `error` holds the failure, and `gridProps` shows
  the error bar with a Retry button. The next window report that covers the block requests it again.
  `retry()` repeats the failed blocks only.
- `refresh()` fetches the rendered blocks again and keeps them on screen until the answers land. It drops every
  other loaded block.
- `gridProps.plugins` <NewBadge /> mounts the guard that keeps a refresh from overwriting a row with a pending save or an open edit. A `plugins` prop of your own replaces it. Put the hook's plugins first: `plugins={[...server.gridProps.plugins, myPlugin]}`. In development, the hook warns once when a refresh runs after a grid rendered rows without the guard.
- `evict(range)` unloads rows. `getLoadedRanges()` and `unloadedCount` report what is loaded.

<Callout type="warn">
  An answer without `totalRowCount` ends the source at the rows of the first block, unless it carries
  `nextCursor` or `hasMore`. Answer the count with every block.
</Callout>

`onRenderedRowsChange` is a core `DataGridProvider` or `DataGrid` prop (see
[Virtualization](/docs/virtualization)). Scroll mode is the first consumer of it, but the prop is generic and
available without the hook, for example for analytics or prefetch.

## Editing loaded rows

The `onDataChange` of the hook merges the edited array back into the sparse rows it already had loaded.
`gridProps` already carries it. Put your own handler in the `onDataChange` option, not in a spread
override, which drops the merge. Send the change to your backend from `onSave`. Editing an unloaded
row is not reachable in the first place. The skeleton-cell handling of the core blocks entering edit
mode on a row that does not exist yet.

## Errors

```tsx
useDataGridServerRows({
  mode: "scroll",
  fetchRows,
  getRowId,
  onError: () => toast.error("Failed to load rows"),
});
```

A failed block stays a hole, rendered as a skeleton row, and the next window report that covers it
requests it again. `error` and the error bar of `gridProps` are the signal that a block failed. The demo's
"Simulate a failed fetch" and "Simulate a permanent failure" buttons show the two cases live. A permanent
failure keeps failing on every scroll, so the Retry button of the error bar is the way out once the cause is
fixed. `retry()` repeats the failed blocks only.

`onLoaded(range)` is the success counterpart of `onError`. It fires once a block resolves, with the
range actually written. The rows commit on the next render. `getLoadedRanges()` includes the range
immediately. A short answer fires with the smaller range. A zero-row answer fires nothing.

For data-fetch libraries (React Query, SWR) and the retry UI, see
[Data fetching & failure recovery](/docs/lazy-loading-advanced).

## Memory & retention

<NewBadge />

Loaded rows stay in the sparse array until a spec change, a count change, a remount, or an explicit call
removes them:

- `server.refresh()` refetches the rendered blocks in place and drops every other loaded block. Use it when
  the dataset behind the same spec is invalidated, for example after a server-side change.
- `server.evict(range)` drops the loaded rows inside `range`. A partial overlap drops the
  intersection only, and the rest stays loaded. Evicted rows refetch on the next scroll into
  them. A sequential source ignores it.
- `server.getLoadedRanges()` returns the loaded ranges, merged and sorted. The result never
  triggers a render. Call it in effects or event handlers.

An eviction policy is a consumer decision. A distance from the visible range is a starting
point:

```tsx
const MIN_DISTANCE = 500;

<DataGridProvider
  {...server.providerProps}
  columns={columns}
  onRenderedRowsChange={(range) => {
    server.providerProps.onRenderedRowsChange(range);
    for (const loaded of server.getLoadedRanges()) {
      if (range.start - loaded.end > MIN_DISTANCE || loaded.start - range.end > MIN_DISTANCE) {
        server.evict(loaded);
      }
    }
  }}
>
  <DataGridRoot {...server.rootProps}>
    <DataGridHeader />
    <DataGridBody />
  </DataGridRoot>
</DataGridProvider>
```

The demo's "Evict loaded rows" button runs `server.evict` over the whole range, so every loaded
row becomes a skeleton and refetches on scroll.

Two behaviors matter when you wire your own policy:

- An in-flight request that started before the evict still lands and marks its range loaded. The
  evicted rows reappear once that request resolves.
- Evicted rows lose edits merged through `onDataChange` that you did not persist. The hook
  does not own persistence. See [Editing loaded rows](#editing-loaded-rows).

Undo and redo compose with the `onDataChange` of the hook. The wiring, the hole-tolerant `getRowId`,
and the `clear()`-on-`refresh()` rule are on the [Undo & redo](/docs/addons/undo-redo#with-scroll-mode)
page.

## Sorting a scroll grid

The sort runs on the server. The hook sets `sortMode="server"`: the grid tracks the sort spec (the
asc → desc → none header cycle, `aria-sort`, the sort indicator, `DataGridSortList`) and calls
`onSortChange`, but never reorders `data`. The hook sends the spec to `fetchRows` and starts the blocks
over when it changes, because fetched blocks hold the *old* order.

```tsx
const server = useDataGridServerRows<Order>({
  mode: "scroll",
  getRowId: (row) => row.id,
  fetchRows: async ({ start, end, signal, spec }) => {
    const answer = await api.orders({ start, end, sorts: spec.sorts, signal });
    return { rows: answer.rows, totalRowCount: answer.total };
  },
});

<DataGrid {...server.gridProps} columns={columns} headerClickBehavior="sort" />
```

A header click sorts only with `headerClickBehavior="sort"`. The default, `"select"`, selects the column and
never changes the spec.

The hook compares the spec by content. `serverSpecKey(spec)` <NewBadge /> returns that content as a string, without the generated `filterId`s. `ServerSpec` is `{ sorts, filters, searchText }`, and both `ServerSpec` and `serverSpecKey` import from `data-grid`. Use it as a query key or an effect dependency for your own request:

```ts
const queryKey = ["orders", serverSpecKey(server.spec)];
```

Use `server.loading` to show a busy state while a request is in flight, for example to dim the grid.

## Filtering a scroll grid

<NewBadge />

The filter runs on the server. The hook sets `filterMode="server"`: the grid tracks the filter spec
(the filter menu, the header filters, `data-filtered`) and calls `onFilterChange`, but never
filters `data`. The view keeps one row per index, so the range from `onRenderedRowsChange` maps to
data indices. The answer carries the filtered row count as `totalRowCount`:

```tsx
const server = useDataGridServerRows<Order>({
  mode: "scroll",
  getRowId: (row) => row.id,
  fetchRows: async ({ start, end, signal, spec }) => {
    const answer = await api.orders({ start, end, filters: spec.filters, signal });
    return { rows: answer.rows, totalRowCount: answer.total };
  },
});

<DataGrid
  {...server.gridProps}
  columns={columns}
  fetchFilterValues={({ columnId, query, filters, signal }) => api.values({ columnId, query, filters, signal })}
/>
```

<ComponentPreview name="data-grid-server-filter-demo" />

Three details make this work:

- **A filter change discards loaded rows.** Fetched blocks hold rows of the old spec. The hook starts
  over at block 0 and takes the new count from the answer.
- **A newer spec wins.** The hook aborts the requests of the old spec and ignores their answers.
- **The header filter lists values from your server.** Pass `fetchFilterValues` to show every
  value of a column, not only the loaded ones. See [Header filter](/docs/addons/toolbar#header-filter).

For the full server contract, see [Server-side data](/docs/recipes/data-fetching/server-side).

`searchText` never narrows anything in the grid. It only highlights and navigates matches over the
rows already in `data`, so a search over a partial array highlights matches in the loaded part
and nothing more. The hook sends `searchText` in the spec, so your backend can search the whole dataset.

<Callout type="warn" title="Client-side sort/filter/search cannot see rows it hasn't fetched">
  Sorting or filtering only reorders or removes rows already in `data`. It has no way to reason
  about the rest of a 100k-row dataset it never loaded. Hand your backend the sort or filter spec,
  and let it decide which rows to serve. `useDataGridServerRows` does this by default.

  A grid with a sparse `data` array that you wire by hand gets a development-only console warning,
  once per grid, when a client sort or filter changes while rows are still unloaded. The warning
  cannot stop the gesture, but it flags the incompatible combination the moment it happens.
  Clipboard and fill across unloaded ranges are blocked the same way as a non-writable column: a
  plain skip, not an error. Aggregates over a scroll-mode grid are unsupported for the same
  reason. Use server-side totals, or compute totals outside the grid from the full dataset (see
  [Pinned rows](/docs/addons/pinned-rows)).
</Callout>

<Callout type="warn" title="DataGridUrlState on a scroll grid">
  `DataGridUrlState` (from [URL state](/docs/addons/url-state)) writes its URL sort, filter, and
  search spec into the store on mount. The hook already sets `sortMode="server"` and `filterMode="server"`, so the
  store keeps the spec and never sorts or filters the partial `data`. Fetch the rows for the spec
  that the URL restored.
</Callout>

## A source with no total

<NewBadge />

A keyset or "has more" API gives a next cursor and no row count. Scroll mode loads such a source
sequentially: each block carries the cursor of the block before. An answer with `nextCursor`, or with neither
`totalRowCount` nor `nextCursor`, starts the sequence:

```tsx
const server = useDataGridServerRows<Order, string>({
  mode: "scroll",
  getRowId: (row) => row.id,
  fetchRows: async ({ cursor, start, end, signal }) => {
    const page = await api.orders({ after: cursor, limit: end - start, signal });
    return { rows: page.items, nextCursor: page.next ?? null };
  },
});

<DataGrid {...server.gridProps} columns={columns} />
```

<ComponentPreview name="data-grid-open-ended-demo" />

- `nextCursor: null` ends the source. Any other value, including `0`, means more rows exist and comes back as `cursor`.
- An API with a "has more" flag and no cursor answers `{ rows, hasMore }`. The request still asks for `[start, end)`, where `start` is the number of rows loaded. `hasMore: false` ends the source. Without the flag, a block that comes back full means more rows exist.
- A `totalRowCount` that comes with a cursor feeds `totalRowCount` and caps the skeleton rows. The source ends when the loaded rows reach it.
- The first call gets `cursor: undefined`. `fetchRows` returns at most `end - start` rows; the hook keeps the first `end - start` rows of a longer answer.
- The next block starts when the rendered rows come within `overscan` rows (default 30) of the loaded end. One block loads at a time.
- The grid shows the loaded rows plus one block of skeleton rows while more exist, so the scroll height
  grows in steps. At the end the skeletons go away and `totalRowCount` holds the final count.
- A cursor that equals the cursor just sent ends the chain, with a warning in development. An empty block ends
  the source. The chain stops at 10,000,000 loaded rows.
- A failed block sets `error`, calls `onError`, and stops the chain. `retry()` repeats the block, and so does the next
  window report.
- A change of the sort, filter, or search text drops the loaded rows and the cursor, and starts again at block 0.
- `refresh()` fetches again from the first block and keeps the loaded rows on screen until the answers land. It
  replaces the rows up to the rendered rows and drops the rest. Rows with a pending save and the row under an edit keep their
  value.
- `evict` and `getLoadedRanges` do nothing useful here: a cursor chain cannot refetch an arbitrary range. The hook keeps
  every loaded row, so stop returning a cursor when the list must not grow without bound.

Without `totalRowCount`, select-all checks the loaded rows and the skeleton rows, so it never means "every matching row". `server.gridProps` carries `totalRowCount: null` and `keepCheckedRows`, so the grid remembers checks by row id and offers `actions.selectAllMatching()`. See [Selection over a server result](/docs/selection-keyboard#selection-over-a-server-result).

## Selecting, copying, and exporting

<NewBadge />

A scroll-mode grid holds unloaded rows as holes. The gestures below work on what the grid holds. None of them fetches a row:

- <kbd>Ctrl</kbd>/<kbd>Cmd</kbd>+<kbd>A</kbd> twice selects the full view, holes included. It selects cells and never checks rows. `getRowIds` for an unloaded row in that selection returns its index-derived placeholder id (`__lazy-unloaded-<index>`), not a real row id.
- Copy copies the loaded cells of the selection. Unloaded ranges are skipped.
- Export covers the loaded rows only: `buildExportRows` skips holes in every scope (see [Import & export](/docs/addons/import-export)).
- The header checkbox and the row markers check rows. With `totalRowCount`, `useDataGridSelectedRows()` lists real ids only.

To act on rows the grid does not hold, ask your server for them. Send the selection value, not the grid's copy:

```tsx
const selected = useDataGridSelectedRows();

async function exportSelection() {
  const rows = await api.exportOrders(
    selected.mode === "ids" ? { ids: selected.ids } : { spec, exceptIds: selected.excludedIds },
  );
  download(rows);
}
```

Without `totalRowCount`, read only the loaded rows from the sparse `data` array (a hole is `undefined`), or keep the rows whose index falls in `server.getLoadedRanges()`. The result is a snapshot that never triggers a render. Call it in an effect or handler.
