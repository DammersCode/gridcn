Before you start, [load server rows](/docs/server-path/load-server-rows). An edit already appears in the grid before your server hears about it. `onSave` sends the edit to your server and tells the grid what the server answered. This step picks the answer.

## Choose the answer [#choose-the-answer]

Find the first line that matches your server:

| If your server | Then `onSave` | Task |
| --- | --- | --- |
| Accepts or refuses a whole change | Returns the request promise. A rejection reverts the change. | [Revert or refetch after a save](/docs/save-server/save-revert) |
| Recomputes values after a write | Waits for the request. The hook then refreshes the rows. | [Revert or refetch after a save](/docs/save-server/save-revert#strategy-b-refetch-on-settle) |
| Refuses some rows of a change | Resolves with `{ rejected }`. The grid reverts only those rows. | [Handle refused saves](/docs/save-server/handle-refused-saves) |
| Rejects one field that the user can fix | Resolves normally and calls `setCellErrors`. | [Show errors on cells](/docs/save-server/show-errors-cells) |

An `onSave` that returns no promise and does not throw cannot revert. The grid tracks a save only while its promise is pending. A thrown error counts as a refusal of the whole change.

## Wire the first save [#wire-the-first-save]

This grid imports `columns` and `Order` from `orders.ts` and `loadPage` from `api.ts`, both from [Load server rows](/docs/server-path/load-server-rows). It sends each change to an API, and the hook fetches the page again after the saves settle. If the request fails, the thrown error reverts the change:

```tsx
"use client";

import { DataGrid } from "@/components/data-grid/data-grid";
import {
  DataGridPaginationBar,
} from "@/components/data-grid-pagination/data-grid-pagination";
import {
  useDataGridServerRows,
} from "@/components/data-grid-server/data-grid-server";
import { columns, type Order } from "./orders";
import { loadPage, sendChange } from "./api";

export function OrdersGrid() {
  const server = useDataGridServerRows<Order>({
    fetchRows: loadPage,
    onSave: sendChange,
  });

  return (
    <>
      <DataGrid {...server.gridProps} columns={columns} className="h-96" />
      <DataGridPaginationBar {...server.pager} />
    </>
  );
}
```

`change.ops` holds one operation (`ops`) for each touched row. Key each request by `rowId`, because a sort or a filter moves the [view index](/docs/concepts/state-view-index).

Where `onSave` goes:

- Pass `onSave` to the hook. The hook runs it and then refreshes the rows by the `refreshAfterSave` policy.
- An `onSave` on `DataGrid` after `{...server.gridProps}` replaces the one of the hook. Then `refreshAfterSave` stops, and the hook warns in development.

The save status of a row:

- `"saving"` while the promise is pending. A refresh keeps the local value of a saving row.
- Cleared after the promise resolves.
- `"failed"` after a refusal.

The `refreshAfterSave` option of the hook defaults to `"settled"`. When every save in flight has settled, the hook calls `refresh()` once. If a save is still in flight 10 seconds after the first one started, the hook refreshes for the saves that settled by then. It skips that refresh when no save has settled. When every save failed, no refresh runs. An `onSave` that returns no promise never triggers a refresh, and `refreshAfterSave: false` turns the refresh off. Then call `server.refresh()` yourself. The refresh brings in the server values. See [Save options](/docs/add-options/server/server-rows-options#save-options) for the other policies.

`onSave` never receives the revert, which has the source `"rollback"`. It never receives a server push, which has the source `"stream"`.

## Result

An edit shows at once. A refused save reverts the edit. An accepted save stays, and the refresh brings in the values that the server computed.
