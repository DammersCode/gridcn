## How it works

History is **operation-based and row-id-based**, not a snapshot stack. Each entry is the operations batch from one
`onDataChange` call (an edit, paste, fill, or delete-range), addressed by row id rather than
array index. So undo and redo keep working correctly across sorts and filters. Undoing an edit
made before a sort still finds and reverts the right row, wherever it sits in the view.

<Callout title="Undo reports a row it cannot reach">
  Before an undo or redo writes, history checks that every row the entry needs is in `data`. If a
  row is missing, history applies nothing, announces the block, and calls `onSkip`. See
  [Rows that are not loaded or gone](#rows-that-are-not-loaded-or-gone).
</Callout>

## Quick start: `useDataGridState`

<Callout title="How this differs from defaultData">
  `useDataGridState` owns the array in your component and passes it as the CONTROLLED `data` prop,
  re-feeding the grid every render. Undo and redo work precisely because of that echo. It is NOT
  the core's `defaultData` semantics (set once, then grid-owned with later props ignored). Reach
  for it only when you actually want history. Otherwise, `defaultData` alone means one less add-on
  to install. See the three-shapes table in
  [Events & state](/docs/events-state#the-three-shapes-an-event-follows) for the
  controlled/uncontrolled/events distinction.
</Callout>

The fastest path wires `useState`, history, and `onDataChange` into one spreadable object:

```tsx
import { useDataGridState } from "@/components/data-grid-history/data-grid-history";

const grid = useDataGridState(initialRows, { getRowId: (row) => row.id });

<DataGridProvider {...grid} columns={columns}>
  <DataGridRoot>
    <DataGridHeader />
    <DataGridBody />
  </DataGridRoot>
</DataGridProvider>;
```

`grid.history` exposes `{ canUndo, canRedo, historySize, undo, redo, clear, record }` for wiring
your own toolbar buttons. `historySize` counts the entries on the undo stack. `clear` empties
both stacks; for a dataset change, pass `datasetKey` instead of calling `clear` by hand (see
[Dataset changes](#dataset-changes)). `record` applies a programmatic change and registers it as
one entry (see [Programmatic changes](#programmatic-changes-record)).
<kbd>Ctrl</kbd>/<kbd>Cmd</kbd>+<kbd>Z</kbd>, <kbd>Ctrl</kbd>/<kbd>Cmd</kbd>+<kbd>Y</kbd>, and
<kbd>Ctrl</kbd>/<kbd>Cmd</kbd>+<kbd>Shift</kbd>+<kbd>Z</kbd> work automatically while focus is in
the grid. The history plugin provides the `undo`/`redo` commands behind those keys.
With the opt-in [`DataGridGlobalShortcuts`](/docs/global-shortcuts) component, undo and
redo also work while focus is on a custom toolbar or anywhere else on the page.
In a `readOnly` grid, the keys do nothing. Your own toolbar buttons call `undo` and `redo`
directly. Those are also no-ops on a `readOnly` grid, so bind their `disabled` to the grid's
`readOnly` flag (see [Read-only grids](#read-only-grids)).

## Composable: `useDataGridHistory`

When you already own the data array through your own state, not the internal `useState` of
`useDataGridState`, wire the history hook directly. It returns one plugin. The grid's store is
the write target, and your controlled-data echo (your `onDataChange` calling your own state
setter) stays exactly where it always was:

```tsx
import { useState } from "react";
import { useDataGridHistory } from "@/components/data-grid-history/data-grid-history";

const [data, setData] = useState<readonly Order[]>(initialRows);
const history = useDataGridHistory({
  capacity: 100, // optional; caps the undo stack, default is generous
});

<DataGridProvider
  data={data}
  columns={columns}
  getRowId={(row) => row.id}
  onDataChange={setData}
  plugins={[history.plugin]}
>
```

The plugin's observer records every change the grid applies (after your own `onDataChange`
runs). The plugin's `undo`/`redo` commands back the keyboard bindings. `history.undo`,
`history.redo`, `history.canUndo`, and `history.canRedo` are the imperative and toolbar-facing
forms of the same history.

## Programmatic changes: `record`

Changes your own app makes (setting the row count, adding a column, rolling back a batch save)
are not gestures, so they never reach `onDataChange`. Register them as a single undo entry with
`record`, passing the row-id-based operation batch for the change. `record` applies the batch to the grid
as one write AND registers it as one entry:

```tsx
const history = useDataGridHistory();

// one call: the change lands in the grid and registers as ONE undo step
history.record(
  {
    source: "app",
    ops: [{ type: "insert", rowId: extraRow.id, row: extraRow, index: data.length }],
  },
  "Add row", // optional entry label
);
```

<Callout type="warn" title="Do not write the array yourself first">
  `record` applies the change through the grid's `commitChange`. If you also apply it to your
  own array, the grid's write and your state land out of order and the echo re-feeds a stale
  array. Call `record` alone, and let the grid's `onDataChange` echo update your state. `label`
  is write-only. It survives undo/redo with the entry, and there is no API to read stack entries
  back.
</Callout>

## Which changes are recorded

History records the changes a user made on purpose: `edit`, `paste`, `fill`, `delete`, `row-operation`,
`import`, `replace`, and `app` (see the `source` field in
[Events & state](/docs/events-state#1-ondatachange--the-flagship-shape)). It never records
`history` (an undo or redo itself). It does not record `stream` by default, so a live feed of
`updateCells` batches never fills the stack or gets undone by accident. Pass `recordSources` to
either hook to change the list:

```tsx
const history = useDataGridHistory({ recordSources: ["edit", "paste", "stream"] });
```

An undo or redo reaches `onDataChange` and `onSave` with `source: "history"`. If `onSave` saves to a
server, it sees the undo as a normal change and saves it.

## Rolling back a failed save

An `onSave` handler sees undo and redo as changes with `source: "history"`. When a save
fails, return the refusal from `onSave` and the grid reverts the change and removes its entry from the
undo stack (see [Server round-trip](/docs/recipes/data-fetching/server-round-trip#strategy-c-acknowledge-each-change)).
To revert a change yourself, call `rollback(change)` with the change the handler received:

```tsx
const history = useDataGridHistory<Row>();

const onSave = async (change: DataChange<Row>) => {
  try {
    await api.save(change);
  } catch {
    history.rollback(change);
  }
};
```

`rollback` applies the inverse change with `source: "rollback"` and removes the entry from the
undo stack, so no dead <kbd>Ctrl</kbd>+<kbd>Z</kbd> step remains. `onSave` never receives a
`"rollback"` change. Neither `"history"` nor `"rollback"` changes are recorded. `createHistory`
exposes the same removal as `discard(change)`.

## Rows that are not loaded or gone

<NewBadge />

An update, delete, or move needs its row in `data`. An insert needs no row. If a row is missing,
`undo` and `redo` apply nothing. What happens to the entry depends on why the row is missing:

| Case | Entry | `onSkip` reason |
|---|---|---|
| Every needed row is in `data` | applied | none |
| A needed row is an unloaded hole in a sparse `data` array | stays on its stack | `"rows-not-loaded"` |
| A needed row is gone from a dense `data` array | dropped | `"rows-gone"` |

For `"rows-not-loaded"`, load the rows and call `undo` again. For `"rows-gone"`, the entry cannot
apply again, so history removes it. The live region announces both cases.

Pass `onSkip` to react, for example to show a toast:

```tsx
const history = useDataGridHistory({
  onSkip: ({ direction, reason, rowIds }) => {
    if (reason === "rows-not-loaded") toast(`Scroll to load ${rowIds.length} rows, then ${direction} again`);
  },
});
```

`onSkip` receives `{ direction, reason, rowIds }`. `direction` is `"undo"` or `"redo"`, and `rowIds` lists
the missing rows. If `onSkip` throws, history logs the error and the grid keeps working.

| Option | Type | Default |
|---|---|---|
| `onSkip` <NewBadge /> | `(ctx: { direction: "undo" \| "redo"; reason: "rows-not-loaded" \| "rows-gone"; rowIds: readonly string[] }) => void` | none |

## Refused undo and redo

<NewBadge />

When `onSave` returns a refusal for an undo or redo (a `{ rejected }` answer), the grid reverts the
change with a `"rollback"` change. History then puts the entry back where it was. A refused undo is on the undo
stack again, and a refused redo is on the redo stack again. A refused ordinary change still drops its
entry.

Undo works on a row with a save in flight. It is one more write, and `onSave` receives it after the
first one.

## Rows the server replaced

<NewBadge />

Two server answers change which entries still make sense:

- A save conflict that adopts the server row, or any change with `serverRowIds`, replaces the
  content of those rows. History removes the operations on those rows from all older entries. An
  entry left with no operations goes. See [Save conflicts](/docs/recipes/data-fetching/server-round-trip#save-conflicts).
- `actions.replaceRowId(oldId, row)` swaps a server-assigned id into a row. History rewrites the
  older entries to the new id, so an earlier edit still undoes. History does not record the swap.

## Capped stack

Pass `capacity` to either hook to bound memory on long editing sessions. The oldest entries drop
once the stack exceeds it. Omit `capacity` for a generous default. `capacity` counts ENTRIES, not
operations: a `record()`/`insertRows` batch of 10k operations is one entry.

## Dataset changes

Pass the identity of your dataset as `datasetKey` to either hook. When the key changes between
renders, the hook clears both stacks without calling `onSkip`, because the swap is your own action.
That keeps undo from reinserting rows of the old dataset after you swap in a new one:

```tsx
const [datasetKey, setDatasetKey] = useState(0);

const grid = useDataGridState(initialRows, {
  getRowId: (row) => row.id,
  datasetKey,
});

// swap the dataset; the stack clears itself on the next render
setDatasetKey((key) => key + 1);
```

A dataset id or a version counter both work. The key only needs to differ between datasets.
Use `clear()` for a reset with no key, for example a "reset to defaults" button.

Without `datasetKey`, a `replaceData` call, a page change, or a new `data` prop leaves entries whose
rows are gone. An undo over such an entry applies nothing and reports `"rows-gone"`, and history drops
the entry. With server pagination, pass `datasetKey={page}` to clear the stacks at once. Without it,
history drops the stale entries one undo at a time. Client pagination keeps all pages in one `data`
array, so it needs no key.

## Read-only grids

A `readOnly` grid refuses writes at the store. History follows that rule end to end: nothing new
records, and `undo` and `redo` are no-ops that keep their entries (popping an unapplied entry
would lose it). Entries recorded before the grid turned read-only keep `canUndo` true while
`undo` does nothing, so gate your toolbar buttons on the grid's `readOnly` flag as well:

```tsx
<DataGrid {...grid} columns={columns} readOnly={readOnly} />

<button disabled={readOnly || !grid.history.canUndo} onClick={grid.history.undo}>
  Undo
</button>
```

The keyboard bindings are gated the same way: on a `readOnly` grid, mod+Z and mod+Y do nothing.

## With scroll mode

`useDataGridServerRows({ mode: "scroll" })` owns the `data` array. That array is sparse: loaded indices hold rows, and
unloaded indices hold `undefined` holes. Spread the hook's `providerProps` (they carry its `onDataChange` echo), and add the history plugin to the `plugins` entry. Every grid write (and
history's own undo/redo writes) flows through the grid's single write path, so the hook
sees every next array through that one echo:

```tsx
const server = useDataGridServerRows<Order>({ mode: "scroll", fetchRows, getRowId });

const history = useDataGridHistory({ datasetKey });

<DataGrid
  {...server.gridProps}
  columns={columns}
  plugins={[...server.gridProps.plugins, history.plugin]}
/>
```

The grid applies a change, emits it, and the hook merges the next array back into its
sparse rows. The history observer records the change from the same emission.

Three rules make the combination safe:

- **The grid's `getRowId` must tolerate holes.** The grid runs `getRowId` on every element of
  the sparse array, including the `undefined` holes. The plain `(row) => row.id` form throws on a
  hole. The hook's own `getRowId` option only sees loaded rows, and
  `server.gridProps.getRowId` is already wrapped to answer a placeholder id for a hole. Pass the
  plain form to the hook and `server.gridProps.getRowId` to the grid, as in the example.
- **Evicted rows block the undo.** If an entry needs a row that the hook evicted or reset, `undo`
  applies nothing, keeps the entry, and reports `"rows-not-loaded"`. Scroll to load the rows, then undo
  again.
- **Clear the stack when the dataset changes.** `server.refresh()` and a dataset swap drop the
  loaded rows the stack references. Pass the dataset's identity as `datasetKey`, so the stack
  clears itself on the next render. If your dataset has no stable identity, call `clear()` in
  the same handler. A tick of `revalidateInterval` <NewBadge /> refetches the same dataset, so it needs no `clear()` and the stack stays.

`undo` also dev-warns once for each grid when it runs over a sparse array.
