A column's `validate` rejects a value before it enters `data`. It takes a function or a Standard Schema, and it runs on a typed edit, a checkbox toggle, paste, fill, `updateCells`, `updateRows`, and import. Delete and Cut write the empty value of the cell type without running `validate`. Live columns for each form are in the [validation example](/docs/validation-examples/validation-example). To check a whole row or wait for an async schema, see [Validate rows and async checks](/docs/editing-cells/validate-rows-cross-field).

## Validate a column [#validation]

`validate` takes one of two forms:

- A function `(value, row) => string | null`. Return a message to reject the value, or `null` to accept it.
- Any [Standard Schema](https://standardschema.dev) for the value, such as Zod, Valibot, ArkType, or Joi. The grid detects a schema by its `"~standard"` key, so the schema needs no adapter.

A schema message joins its issues with `"; "` and prefixes an issue path as `a.b: message`.

A cell type can declare `validate` as a default for its columns. The column's own `validate` wins. Undo and redo replay recorded changes and skip `validate`.

Install zod first with `pnpm add zod`. This grid uses both forms:

```tsx
import { z } from "zod";
import { DataGrid, defineColumns } from "@/components/data-grid/data-grid";

type Person = { id: string; age: number; score: number };

const columns = defineColumns<Person>()([
  {
    id: "age",
    header: "Age",
    accessorKey: "age",
    type: "number",
    validate: (value) =>
      typeof value === "number" && value < 18 ? "Must be 18 or older" : null,
  },
  {
    id: "score",
    header: "Score",
    accessorKey: "score",
    type: "number",
    validate: z.number().int().min(0).max(100),
  },
]);

export function People({ people }: { people: Person[] }) {
  return <DataGrid defaultData={people} columns={columns} />;
}
```

### Validate an email [#validate-an-email]

<NewBadge />

This column rejects text that does not look like an email address. An empty cell passes, so the field stays optional:

```tsx
import { defineColumns } from "@/components/data-grid/data-grid";

type Contact = { id: string; email: string };

const EMAIL = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;

const columns = defineColumns<Contact>()([
  {
    id: "email",
    header: "Email",
    accessorKey: "email",
    validate: (value) =>
      typeof value === "string" && value !== "" && !EMAIL.test(value)
        ? "Enter an email such as name@example.com"
        : null,
  },
]);
```

A schema works too, for example `validate: z.email()` with Zod 4. Your server checks the address again, because the grid only checks the format.

<Callout type="warn" title="A rejected edit stays open">
  The editor stays open on a rejected value and shows the message. The value never enters `data`.
  A soft rule is the exception. A rejected checkbox toggle has no editor: the cell keeps its old value and shows no message.
</Callout>

The message <NewBadge /> shows as an error line next to the open editor. The line escapes the cell and widens to its text, up to 16rem. It flips above the cell at the bottom edge of the grid. At the side edges, it anchors to the end side of the cell. An editing cell does not clip its content, so a custom `Editor` wider than its cell spills over the neighbors.

If a validator throws or its promise rejects, the grid rejects the value and shows the error message. A throwing validator blocks the edit even on a soft column.

## Soft rules [#soft-rules-oninvalid]

By default a rejection blocks the commit. Set `onInvalid: "warn"` to commit the value and flag the cell instead. The flag uses the same ring, tint, and hover tooltip as a server error. The next valid commit of that cell clears it. The editor closes, because the commit succeeded. [Validation example](/docs/validation-examples/validation-example#blocking-and-soft-rules) compares a blocking rule with a soft rule.

A rejection carries no transformed value, so a soft commit stores the raw input. The flag works with the function form and with sync and async schemas. Paste, fill, `updateCells`, and import still drop rejected cells in a soft column. Import writes an empty value.

This column flags a note over 12 characters:

```tsx
import { DataGrid, defineColumns } from "@/components/data-grid/data-grid";

type Note = { id: string; text: string };

const columns = defineColumns<Note>()([
  {
    id: "text",
    header: "Text",
    accessorKey: "text",
    validate: (value) =>
      typeof value === "string" && value.length > 12
        ? "Max 12 characters"
        : null,
    onInvalid: "warn",
  },
]);

export function Notes({ notes }: { notes: Note[] }) {
  return <DataGrid defaultData={notes} columns={columns} />;
}
```

## Transforms [#transforms-are-committed]

A schema can transform a value. On success the grid commits the schema output, not the raw input. Bulk paths commit the output too.

This column stores the trimmed text:

```tsx
import { z } from "zod";
import { defineColumns } from "@/components/data-grid/data-grid";

type Contact = { id: string; name: string };

const columns = defineColumns<Contact>()([
  {
    id: "name",
    header: "Name",
    accessorKey: "name",
    validate: z.string().trim().min(1, "Required"),
  },
]);
```

## Report rejected cells [#onvalidationerror]

After a paste, a fill, or an `updateCells` call settles with at least one rejected cell, `onValidationError` fires. The grid has applied the accepted cells by then. `updateCells` also lists each rejected patch in its return value. Import reports its rejected cells through `rejected` in `onImport`, not here. See [Control the import](/docs/import-export/control-import).

{/* props: GridValidationErrorEvent */}

| Prop | Type |
|---|---|
| `source` | `"paste" \| "fill" \| "stream" \| "replace"` |
| `rejected` | `GridBulkValidationError[]` |

`"stream"` marks an `updateCells` or `updateRows` call, and `"replace"` a find-and-replace batch. Each entry has `rowId`, `columnId`, `viewRowIndex`, `value`, and `message`. A row outside the view reports `viewRowIndex: -1`.

## Server mode

Validation runs in the browser in every data mode: local data, client and server pagination, scroll mode, controlled state, server sort, and server filter. `validate` runs before the grid emits `onDataChange` and `onSave`, so a blocking rule keeps a refused value from your server. A soft rule, a `validateRow` flag, `skipValidation`, a Delete or Cut clear, undo or redo, and `actions.commitChange` let the value through. Check the same rules on your server.

A server can still refuse a value after it commits. Paint that refusal with `actions.setCellErrors`. It marks the cell without a data change. See [Show errors on cells](/docs/save-server/show-errors-cells).
