A column's `validate` rejects a value before it enters `data`. It takes a function or a Standard Schema, and it runs on a typed edit, a checkbox toggle, paste, fill, `updateCells`, `updateRows`, and import. `validateRow` checks a whole row after a write and flags cells without blocking the write. Live columns for each form are in the [validation example](/docs/validation-examples/validation-example).

## Validate a column [#validation]

`validate` takes one of two forms:

- A function `(value, row) => string | null`. Return a message to reject the value, or `null` to accept it. The function is your code, so side effects work.
- Any [Standard Schema](https://standardschema.dev) for the value, such as Zod, Valibot, ArkType, or Joi. The grid detects a schema by its `"~standard"` key, so the schema needs no adapter.

A schema message joins its issues with `"; "` and prefixes an issue path as `a.b: message`.

A cell type can declare `validate` as a default for its columns. The column's own `validate` wins. Each of those paths resolves `column.validate ?? cellType.validate`. Undo and redo replay recorded changes and skip `validate`.

This grid uses both forms:

```tsx
import { z } from "zod";
import { DataGrid, defineColumns } from "@/components/data-grid/data-grid";

type Person = { id: string; age: number; score: number };

const columns = defineColumns<Person>()([
  {
    id: "age",
    header: "Age",
    accessorKey: "age",
    type: "number",
    validate: (value) =>
      typeof value === "number" && value < 18 ? "Must be 18 or older" : null,
  },
  {
    id: "score",
    header: "Score",
    accessorKey: "score",
    type: "number",
    validate: z.number().int().min(0).max(100),
  },
]);

export function People({ people }: { people: Person[] }) {
  return <DataGrid defaultData={people} columns={columns} />;
}
```

<Callout type="warn" title="A rejected edit stays open">
  The editor stays open on a rejected value and shows the message. The value never enters `data`.
  A soft rule is the exception.
</Callout>

The message shows as an error line <NewBadge /> next to the open editor. The line escapes the cell and widens to its text, up to 16rem. It flips above the cell at the bottom edge of the grid. At the side edges, it anchors to the end side of the cell. An editing cell does not clip its content, so a custom `Editor` wider than its cell spills over the neighbors. See [Blocking and soft rules](/docs/validation-examples/validation-example#blocking-and-soft-rules).

If a validator throws or its promise rejects, the grid rejects the value and shows the error message. A throwing validator blocks the edit even on a soft column.

## Soft rules [#soft-rules-oninvalid]

By default a rejection blocks the commit. Set `onInvalid: "warn"` to commit the value and flag the cell instead. The flag uses the same ring, tint, and hover tooltip as a server error. The next valid commit of that cell clears it. The editor closes, because the commit succeeded. [Validation example](/docs/validation-examples/validation-example#blocking-and-soft-rules) compares a blocking rule with a soft rule.

A rejection carries no transformed value, so a soft commit stores the raw input. The flag works with the function form and with sync and async schemas. In the function form, return `null` to skip the rule for a row. Paste, fill, and `updateCells` still drop rejected cells in a soft column.

This column flags a note over 12 characters:

```tsx
import { DataGrid, defineColumns } from "@/components/data-grid/data-grid";

type Note = { id: string; text: string };

const columns = defineColumns<Note>()([
  {
    id: "text",
    header: "Text",
    accessorKey: "text",
    validate: (value) =>
      typeof value === "string" && value.length > 12
        ? "Max 12 characters"
        : null,
    onInvalid: "warn",
  },
]);

export function Notes({ notes }: { notes: Note[] }) {
  return <DataGrid defaultData={notes} columns={columns} />;
}
```

## Transforms [#transforms-are-committed]

A schema can transform a value. On success the grid commits the schema output, not the raw input. A transforming schema changes what data your grid stores. Bulk paths commit the output too.

This column stores the trimmed text:

```tsx
import { z } from "zod";
import { defineColumns } from "@/components/data-grid/data-grid";

type Contact = { id: string; name: string };

const columns = defineColumns<Contact>()([
  {
    id: "name",
    header: "Name",
    accessorKey: "name",
    validate: z.string().trim().min(1, "Required"),
  },
]);
```

## Async schemas [#async-schemas]

A Standard Schema can return a promise, for example for a uniqueness check. The function form is synchronous. The same column definition covers a single edit and every bulk path:

```tsx
import { z } from "zod";
import { defineColumns } from "@/components/data-grid/data-grid";

async function isSkuFree(sku: string) {
  const res = await fetch(`/api/sku/${encodeURIComponent(sku)}`);
  return res.ok;
}

type Item = { id: string; sku: string };

const columns = defineColumns<Item>()([
  {
    id: "sku",
    header: "SKU",
    accessorKey: "sku",
    validate: z.string().refine(isSkuFree, "Already in use"),
  },
]);
```

In a single-cell edit, the editor stays open while the schema resolves. The built-in text and number inputs turn `readOnly`, never `disabled`, so <kbd>Escape</kbd> still cancels. If the schema resolves with issues, the message shows like a sync rejection and editing continues. If it succeeds, the grid commits `result.value` and then applies the pending move from <kbd>Enter</kbd>.

<kbd>Escape</kbd>, a newer commit, an unmounted cell, or a restarted edit on the same cell invalidates the pending check. The grid drops its result silently.

### On bulk paths [#on-bulk-paths]

Paste, fill, and `updateCells` hold the batch while an async schema resolves:

- The grid runs at most 32 validations at once. A paste of 10,000 cells makes 32 calls at a time.
- Nothing changes until every verdict is in. The accepted cells then commit together as one change.
- A rejected cell drops and the other cells still commit.
- A second paste, a sort or filter change, a deleted target row, or an unmounted grid drops the held batch silently. Paste and fill each supersede only their own batch. Other writes also drop a held `updateCells` batch. [Stream updates](/docs/rows-live-data/stream-updates#what-does-not-change) lists them.

Import validates each cell the same way. It writes an empty value for a rejected cell. See [Import](/docs/import-export/import).

<Callout type="warn" title="A slow schema makes a slow batch">
  A 200 ms network call across 10,000 cells takes about 60 seconds at 32 calls at a time, and the
  grid shows no progress. For a large paste against a remote check, validate the whole block once
  with the `processPaste` override of [Clipboard](/docs/clipboard-undo/clipboard).
</Callout>

`actions.updateCells(patches, { skipValidation: true })` skips `validate` for a trusted feed.

## Report rejected cells [#onvalidationerror]

After a paste, a fill, or an `updateCells` call settles with at least one rejected cell, `onValidationError` fires. The grid has applied the accepted cells by then. `updateCells` also lists each rejected patch in its return value.

{/* props: GridValidationErrorEvent */}

| Prop | Type |
|---|---|
| `source` | `"paste" \| "fill" \| "stream" \| "replace"` |
| `rejected` | `GridBulkValidationError[]` |

`"stream"` marks an `updateCells` or `updateRows` call, and `"replace"` a find-and-replace batch. Each entry has `rowId`, `columnId`, `viewRowIndex`, `value`, and `message`. A row outside the view reports `viewRowIndex: -1`. See [Edit and validation events](/docs/events-state/edit-validation-events).

## Cross-field rules [#cross-field-rules-validaterow]

`validateRow` checks a row after a write gesture commits: an edit, a paste, a fill, a clear, `updateCells`, or `updateRows`. It runs once per touched row, with all cells of the gesture applied, so the verdict never depends on column order.

To flag cells, return a `columnId` to message map. If the row is fine, return `null`. The flags use the same display as server errors: ring, tint, tooltip, and `aria-invalid`. The values still commit. Any later write that makes the row consistent clears the flags, whichever column it writes.

This grid flags a discount above the price:

```tsx
import { DataGrid, defineColumns } from "@/components/data-grid/data-grid";

type Line = { id: string; price: number; discount: number };

const columns = defineColumns<Line>()([
  { id: "price", header: "Price", accessorKey: "price", type: "number" },
  {
    id: "discount",
    header: "Discount",
    accessorKey: "discount",
    type: "number",
  },
]);

export function Lines({ lines }: { lines: Line[] }) {
  return (
    <DataGrid
      defaultData={lines}
      columns={columns}
      validateRow={(row) =>
        row.discount > row.price ? { discount: "Discount above price" } : null
      }
    />
  );
}
```

`validateRow` does not run on a row insert or duplicate, because a fresh default row is incomplete. It does not run on a row delete, or after you replace the `data` array.

`validateRow` <NewBadge /> also runs for the rows that `actions.commitChange` inserts or updates, for every change source except `"stream"`. An import that replaces the data with `delete` and `insert` operations validates each imported row, and does not validate the deleted rows. An undo, a redo, and a rollback validate the rows they restore, so a cross-field error that the undone edit caused goes away. A newer change that touches the row cancels its pending verdict.

`validateRow` can return a promise. The write commits first. The verdict merges after the promise settles. A newer verdict for the same row replaces a pending one. The grid drops a verdict for a row that is gone, and a rejected promise adds no error.

`validateRow` receives `{ signal }` <NewBadge /> as its third argument. The signal aborts when a newer verdict for the same row replaces this one, when the row is gone, and when the grid unmounts. The grid drops an aborted verdict.

## Server mode

Validation runs in the browser in every data mode: local data, client and server pagination, scroll mode, controlled state, server sort, and server filter. `validate` runs before the grid emits `onDataChange` and `onSave`, so a blocking rule keeps a refused value from your server. A soft rule, a `validateRow` flag, and `skipValidation` let the value through. Check the same rules on your server.

A server can still refuse a value after it commits. Paint that refusal with `actions.setCellErrors`. It marks the cell without a data change. See [Show errors on cells](/docs/save-server/show-errors-cells).
