Every callback on these pages except `onFill` is a prop of `DataGrid` or `DataGridProvider`. `onFill` is an option of `useDataGridFill`. Other add-ons document their own callbacks on their option pages. A callback belongs to a controlled prop, reports an event, or is a gate. The tables below name the callback for each need and link its payload.

The grid has no copy event and no scroll-position callback. A paste reports through `onDataChange` with `source: "paste"`. `onRenderedRowsChange` reports the rendered rows. A new function identity for `onCellClick`, `onCellDoubleClick`, or `onCellContextMenu` re-renders no cell.

The complete list of props is the `DataGridSyncProps` type. The [DataGridProvider](/docs/components-props/data-grid-provider) page lists every prop.

## Three shapes [#the-three-shapes-an-event-follows]

### Controlled and uncontrolled props [#controlled-pairs]

A controlled prop and its callback follow the React rule for `value` and `defaultValue`. Pass the value prop to control the state. Pass the `default` prop to seed it once. The grid ignores later changes to a `default` prop.

| State | Value prop | Callback | Seed prop |
|---|---|---|---|
| Rows | `data` | `onDataChange` | `defaultData` |
| Sort | `sortState` | `onSortChange` | `defaultSortState` |
| Filters | `filterState` | `onFilterChange` | `defaultFilterState` |
| Quick search | `searchText` | `onSearchTextChange` | `defaultSearchText` |
| Selection | `selection` | `onSelectionChange` | `defaultSelection` |
| Column layout | `columnLayout` | `onColumnLayoutChange` | `defaultColumnLayout` |

Omit the value prop and the grid owns the state. The callback still fires.

Three update rules apply:

- You answer first: `sortState`, `filterState`, and `searchText`. With the value prop, the grid writes nothing, and the callback receives the next value. When you pass the new value, the view changes. Without the value prop, the grid writes the change, then fires the callback.
- `data`: the grid applies the change at once and reports it. The next time the grid reads your `data`, it replaces its rows with that array, so pass `next` back.
- The grid answers first: `selection` and `columnLayout`. The grid applies the gesture and fires the callback at once. A value you pass back that equals the fired value changes nothing. Any other value applies without firing the callback.

For `columnLayout`, you control each part (`widths`, `order`, `pins`, `hidden`) on its own. An omitted part stays with the grid.

### Callbacks that report [#notifications]

These callbacks say what happened and change nothing. `onCellClick`, `onCellDoubleClick`, `onCellContextMenu`, `onActiveCellChange`, `onColumnResizing`, `onRenderedRowsChange`, `onEditEnd`, `onValidationError`, and `onSaveRejected` only report.

### Gates [#gates]

A gate runs before the grid acts and can stop the action:

- `onEditStart` returns `false` to stop an edit.
- `onBeforeDeleteRows` returns `false` to stop a row delete.
- `onFill` calls `preventDefault()` to stop a fill.
- `processPaste` returns `false` to stop a paste.

`onSave` is a save acknowledgement. It is neither a reporting callback nor a gate: see [onSave](/docs/events-state/data-change-events#onsave).

`onEditStart`, `onBeforeDeleteRows`, `processPaste`, `processCellFromClipboard`, `createRow`, and `duplicateRow` also accept a promise. A pending promise blocks a second request of the same kind. A rejection cancels the action. `validateRow` also accepts a promise. When it rejects, the row gets no verdict.

## Callback timing and errors [#callback-errors]

<NewBadge />

A callback runs synchronously, after the grid writes the change. Inside the callback, the store holds the new state. One exception: when a filter prop resets a paged grid to page 1, `onPageChange(1)` runs in a microtask after the sync. With a controlled value prop, the grid writes nothing, and the callback receives the next value.

These callbacks rethrow: `onSortChange`, `onFilterChange`, `onSearchTextChange`, `onPageChange`, `onPageSizeChange`, `onColumnLayoutChange`, `onColumnResizing`, `onValidationError`, and `onEditEnd`. If one of them throws, these rules apply:

- The change stays written.
- The other callbacks of the change still run. For example, a filter change resets a paged grid to page 1. A throwing `onFilterChange` still lets that `onPageChange` fire.
- After they ran, the grid rethrows the first error to the caller, for example a click handler or your `setSorts` call.

These callbacks log: `onSelectionChange`, `onActiveCellChange`, and the `onEditEnd` of an edit that a view change ends. If one of them throws, the grid prints `[data-grid] <callback> threw:` and the error as a console error. The grid's other updates still run.

`onGateAborted` and `onRowActionSkipped` swallow a throw. A development build prints `[data-grid] <callback> threw:` and the error as a warning.

`onDataChange` and `onSave` follow the rules of [Data change events](/docs/events-state/data-change-events#ondatachange).
