A row has three addresses, and the grid APIs mix them. A call that takes the wrong one acts on another record after a sort. This page names the addresses and says which one each API takes.

## Three addresses

| Address | Meaning | Where you meet it |
| --- | --- | --- |
| Data index | The position in your `data` array. | The second argument of `getRowId`. |
| View index | The position in the sorted and filtered list that the user sees. | `ViewCoord`, `insertRow`, `insertRows`, `deleteRows`, and `duplicateRows`. |
| Row id | The stable id that `getRowId` returns. | `CellRef`, `deleteRowsById`, and the operations of a `DataChange`. |

When you omit `getRowId`, the grid reads the `id` field of the row. A row without a string or number `id` throws an error.

A column has the same split. A column id names the column for good. The column part of a `ViewCoord` counts the visible columns in display order, without the row marker column.

## What rebuilds the view

The grid keeps a `viewIndex` array. Its entry at a view index is the data index of the row shown there. These changes rebuild it:

- With `sortMode="client"`, a sort.
- With `filterMode="client"`, a filter.
- A new `data` array.
- An inserted, duplicated, or deleted row.
- A call to `actions.reconcileView()`.

A mode set to `"server"` skips its own step, because your backend applies the sort or the filter. A search never narrows the view. It highlights matches and moves between them.

A rebuild changes the view index of rows. It never changes a row id.

## Which address to keep

A view index is valid for the render that read it. Keep a row id or a `CellRef` for anything that outlives a render.

- The active cell and the selection sit in the store as view indexes. After a rebuild, the grid moves them back onto their records. [Selection model](/docs/concepts/selection-model#selection-follows-records) lists the rules.
- Cell events such as `onActiveCellChange` hand out both addresses. `ViewCellRef` holds the row id, the column id, and the view position at the time of the event.
- Cell actions take a `CellRef`. Each has an `*At` variant, such as `selectCellAt`, that takes a `ViewCoord`.
- An edit, paste, fill, or cleared selection can write a column that the active sort or filter reads. The rows then keep their old view index, and `useDataGridViewStale` returns `true`. `actions.reconcileView()` rebuilds the view. See [Stream updates](/docs/rows-live-data/stream-updates).

## Read an address

Inside a `DataGridProvider`, these hooks convert between the addresses:

- `useDataGridViewIndex()` returns the `viewIndex` array.
- `useDataGridRowId(viewRowIndex)` returns the row id at a view index.
- `useDataGridRowIdToViewRow()` returns a map from row id to view index.
- `useDataGridRow(viewRowIndex)` returns the row object.

[Store hooks](/docs/types-hooks/store-hooks) describes each hook.

### Rows without an index

- A row that scroll mode has not loaded yet is a hole in `data`. `useDataGridRowId` returns an index-derived placeholder id for it, and `useDataGridRow` returns `undefined`. The placeholder stays valid only while the hole keeps its data index.
- The rows of a plugin band belong to the plugin. They have no data index and no view index. See [Plugin overlays](/docs/plugins/plugin-overlays#row-bands).
