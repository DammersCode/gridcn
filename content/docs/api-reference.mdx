### Imperative handle <NewBadge />

The `ref` prop receives the grid's `DataGridApi`: `actions`, `store`, `scrollTo`, `focus`,
`startEditing`, `stopEditing`, `getSelection`, `setSelection`, `getRow`, and `getViewRowIds`. The
object is stable for the grid's lifetime, so a toolbar or effect can hold it and call into the
grid without re-rendering when the grid changes:

```tsx
const gridRef = useRef<DataGridApi<Order> | null>(null);

<DataGrid ref={gridRef} data={orders} columns={columns} getRowId={(o) => o.id} />

// from a toolbar button or an effect
gridRef.current?.scrollTo({ rowId: order.id, columnId: "symbol" });
gridRef.current?.actions.selectCell({ rowId: order.id, columnId: "symbol" });
```

- `getSelection`, `getRow`, and `getViewRowIds` are snapshots at call time. They never
  re-render the calling component.
- `getViewRowIds` returns one entry per view row, in view order, so entry `i` is always view
  row `i`. An unloaded row of a lazy grid gives its placeholder id (`__lazy-unloaded-<index>`),
  the same id `useDataGridRowIds` returns.
- `setSelection` applies a whole selection (a range, a range stack, row and column channels)
  in stable `CellRef` terms, or clears the selection with `null`. It emits like a gesture:
  `onSelectionChange` fires when the result differs from the grid's current value. Selecting a
  single cell stays `actions.selectCell(ref)`.
- `startEditing` opens an edit session at the named cell; `stopEditing` discards the draft
  without committing. `startEditing` does nothing on a `readOnly` grid, on a `readOnly` cell,
  and on a cell whose type declares `activate`, like the keyboard edit gestures.
- `focus` scrolls the active cell into view and lands on it. With no active cell, it focuses the
  grid, whose onboarding seeds (0,0). It is a no-op while an edit session is open.
- For manual composition (`DataGridProvider` + `DataGridRoot`), pass the `ref` to
  `DataGridProvider`, or call `useDataGridApi(ref)` in any component under the provider. A
  toolbar next to `DataGridRoot` can use the handle. `scrollTo` and `focus` do nothing until a
  `DataGridRoot` mounts.

### `store`: external store ownership

By default `DataGridProvider` creates and owns its store. When the store must live OUTSIDE the
provider's render (a panel beside the grid that reads it without a provider above, one store
shared by several provider trees) create it with `useDataGridStoreProps(props)` and feed it in
through the `store` prop (on both `DataGridProvider` and `DataGrid`):

```tsx
const gridRef = useRef<DataGridApi<Order> | null>(null);
const { store } = useDataGridStoreProps({ data, columns, getRowId, onDataChange: handleDataChange });

function handleDataChange(next: readonly Order[], change: DataChange<Order>) {
  setData(next);
  saveOrders(change.ops).catch((error) => {
    gridRef.current?.actions.setCellErrors(parseFieldErrors(error)); // the rejection lands after mount
  });
}

return (
  <>
    <PageErrorPanel store={store} /> {/* beside the grid — no provider above it */}
    <DataGrid ref={gridRef} store={store} />
  </>
);
```

- `useDataGridStoreProps` takes the same sync props as the provider and keeps the store in sync
  with them on every render. Pass it the same live props the grid renders from.
- With `store` set, the provider is a pure context shell: it creates nothing, syncs nothing, and
  subscribes to nothing. Your `useDataGridStoreProps` call owns the store.
- Imperative calls from your own component (a server follow-up in `onDataChange`, a WebSocket
  push of validation errors) need no lifted store: by the time the async handler resolves the
  handle is set, so `gridRef.current?.actions.…` reaches the same actions. The lifted `actions`
  is the only actions source on the first render, before the handle is set.
- `store.getState()` and `store.subscribe()` are reachable from outside React for anything the
  selector hooks can't reach. The handle's read-only `store` offers the same pair once the grid
  is mounted.

### `plugins` <NewBadge />

`readonly DataGridPlugin[]`, optional, on both `DataGridProvider` and `DataGrid`. Each entry is
an add-on (or your own code) that reaches into the grid through six optional members: an
`Overlay` component, a `rowBands` contribution, an `onDataChange` observer, `commands`, a
`keymap`, and a `Mount` component. Array order is precedence and visual order.
See [Plugins](/docs/plugins) for the full contract, and
[Multiplayer presence](/docs/addons/presence), [Fill handle](/docs/addons/fill), and
[Undo & redo](/docs/addons/undo-redo) for three first-party consumers.

<Callout title="Identity is entry-wise">
  The grid compares the list entry-wise (same length, same `name` per entry, every member
  identity-equal) so a fresh `[plugin]` array per render is harmless while the plugin keeps its
  identity. A changed plugin member re-resolves the grid's plugins and remounts the plugin
  components whose type changed. A plugin object attaches to one grid; the same object on two
  grids dev-errors, and the second grid excludes it.
</Callout>

### Hooks

State access is hooks only. Call them under `DataGridProvider`. The one way out is
`useDataGridStoreProps` (above). It hands you the store itself for code outside the
provider's subtree. The full list lives in `store/hooks.ts`. These are the ones you will reach
for most:

- `useDataGridActions()`: the single stable actions object (`setSorts`, `setFilters`,
  `setSearch`, `setColumnWidth`, `setColumnOrder`, `setColumnPin`, `setColumnHidden`,
  `setColumnLayout`, `setSelection`,
  `autosizeColumns`, `selectCell`, `extendTo`, `startEditing`, `commitCellEdit`, `deleteSelection`,
  `updateCells`, `updateRows`, `commitChange`, `reconcileView`, `setCellErrors`, `clearCellErrors`,
  plus the row
  operations
  `insertRow`, `duplicateRows`, `deleteRows`. See [Row operations](/docs/row-operations)). The
  complete list is the `DataGridActions` type. `commitChange(change)` applies a whole
  `DataChange` operation batch in one write and emits `onDataChange` once, so it lands on the undo
  stack as a single entry; it is a no-op on a `readOnly` grid and does not revalidate values.
- `useDataGridViewStale()`: true when a write left the sorted order stale: a deferred
  `updateCells` batch, or an edit, paste, fill, or cleared selection that touched a column the
  active sort or filter reads. See [Streaming updates](/docs/streaming-updates).
- `useDataGridCellTypes()`: the resolved cell-type registry (built-ins or consumer-provided),
  for tooling that needs to inspect or resolve a column's renderer/editor.
- `useDataGridActiveColumn()`: the active cell's column index (or `null`), for tooling that only
  cares about the active column.
- `useDataGridActiveCell()`, `useDataGridSelection()`, `useDataGridGetSelectionValues()`, `useDataGridEditing()`
- `useDataGridSortState()`, `useDataGridFilterState()`, `useDataGridSearchText()`
- `useDataGridVisibleColumns()`, `useDataGridAllColumns()`, `useDataGridColumnWidth(id)`,
  `useDataGridIsColumnHidden(id)`
- `useDataGridLabels()`, `useDataGridKeymap()`, `useDataGridReadOnly()`
- `useDataGridScrollToCell()`: imperative scroll to a `CellRef`.
  `useDataGridScrollToCellAt()`: the same scroll to a `ViewCoord`.
- `useDataGridApi(ref?)`: the grid's imperative handle (`DataGridApi`); see
  [Imperative handle](#imperative-handle).
- `useDataGridCellErrors()`: the full post-commit server-error map. See
  [Editing & cell types: Server errors](/docs/editing-cell-types#server-errors).
- `createDataGridSelector<TData>()`: returns a typed raw store selector hook. Create the hook
  once at module scope and name it `use…`, for example
  `const useOrderSelector = createDataGridSelector<Order>()`. `TData` types `state.data`, so a
  selector that reads rows gets them back typed. The hook takes `(selector, eq?)`; `eq` (default
  `Object.is`) controls re-renders.
- `useDataGridRow<TData>(viewRowIndex)`: the typed row at a view (display) index. Omit
  `TData` for `unknown`, the previous shape.

`onSelectionChange`, `onColumnLayoutChange`, and every other event source are covered in full on
[Events & state](/docs/events-state).

## `ColumnDef<TData, TValue>`

<AutoTypeTable path="./registry/default/blocks/data-grid/types.ts" name="ColumnDef" />

<Callout title="Prefer defineColumns over typing ColumnDef[] by hand">
  `defineColumns<TData>()([...])` infers `TValue` per column from `accessorKey` or `accessorFn`,
  and narrows `options` and `validate` through the cell type's key in `GridCellTypes`, catching
  `accessorKey` typos and type-key typos at compile time. See
  [Quick start](/docs/quick-start#define-columns).
</Callout>

`AnyColumnDef` (`ColumnDef<unknown, unknown, any>`) is the row-agnostic shape that the store and
its hooks (`useDataGridVisibleColumns()`, `useDataGridAllColumns()`, and similar hooks) actually
traffic in. Reach for it when you write custom column UI that does not know its `TData` generic.

<Callout title="validate's type: a union, and a 3rd type parameter">
  `validate` is `((value: TValue, row: TData) => string | null) | StandardSchemaV1<TValue>`: the
  function form, or any [Standard Schema](https://standardschema.dev). `ColumnDef` has a 3rd type
  parameter, `TValidate` (defaults to `TValue`), because the function-or-schema union does not
  stay assignable when the row-agnostic `AnyColumnDef` erases its type parameters to `unknown`.
  So `AnyColumnDef` erases `TValidate` to `any` instead. This never affects how you author
  `validate` on a concretely-typed column through `defineColumns`. `StandardSchemaV1.InferInput<S>`
  and `InferOutput<S>` are exported from `types.ts` for inspecting a schema's own input and output
  types.
</Callout>

## `CellType<TData, TValue, TOptions>`

<AutoTypeTable path="./registry/default/blocks/data-grid/types.ts" name="CellType" />

Register custom types through the `cellTypes` prop of `DataGridProvider`. The prop **merges over
the built-ins** (`text`, `number`, `checkbox`, `select`, `date`): unnamed built-ins keep working,
a key that names a built-in replaces it, and a key set to `null` removes that type. Wrap the type
in `defineCellType(key, type)` once your `GridCellTypes` augmentation is in place: it checks the
key and the type's value/options against the augmentation at the definition, and returns the
entry as-is. See [Recipes](/docs/recipes/editing/custom-cell-type) for a worked example.

### `GridCellTypes`

This interface map gives `defineColumns` its per-type inference. Augment it through declaration
merging in your own module to give a custom cell type the same compile-time `options` and value
narrowing as the built-ins:

```ts
declare module "@/components/data-grid/types" {
  interface GridCellTypes {
    currency: { value: number | null; options: { currency: string } };
  }
}
```

Adjust the module path to wherever your `components.json` aliases actually placed `types.ts`.

### `defineCellType(key, type)` <NewBadge />

A compile-time gate for a custom cell type: `key` must be a cell-type key of `GridCellTypes`
(including your augmentation), and `type` must match that key's declared `value` and `options`.
It costs nothing at runtime and returns the entry unchanged, ready for the `cellTypes` registry.

### `useCellEditor(props, codec)` <NewBadge />

The text-input editor primitive the built-in `text` and `number` editors are built from. It owns
the draft state (seeded from `props.initialText`, or `codec.toDraft(value)` when there is
none), the end-caret focus, and the one-shot commit guard (re-armed when `rejectionCount`
rises). It also binds Enter (commit, move down), Escape (cancel), and blur (commit in place).
During IME composition, Enter and Escape do nothing. `codec` is `{ toDraft, toValue }`. `toValue`
must never throw and must return your type's `clearValue` result for text it cannot parse. The
hook returns `{ ref, value, onChange, onKeyDown, onBlur, readOnly, "aria-label", "aria-busy", dir }`.
Spread the bindings onto your input and pass its `ref`. `readOnly` mirrors `props.pending`,
`aria-label` is the column label, `aria-busy` is `true` while `props.pending` is true, and `dir`
is `"auto"`.

## Other exported types

- `DataGridApi<TData>`: the imperative handle of one grid: `actions`, `store`, `scrollTo`,
  `focus`, `startEditing`, `stopEditing`, `getSelection`, `setSelection`, `getRow`, and
  `getViewRowIds`. From `<DataGrid ref>` or from `useDataGridApi`. See
  [Imperative handle](#imperative-handle).
- `CellRef` (`{ rowId, columnId }`): the stable identity of a cell: your `getRowId` value plus
  a column id. Sorting, filtering, and reordering never change it. Cell actions take a
  `CellRef` by default; each also has an `*At` variant that takes a `ViewCoord` instead.
- `CellRange` (`{ start: CellRef; end: CellRef }`): the two opposite corners of a rectangular
  selection; either diagonal order.
- `SelectionState` (`{ anchor, range, rangeStack, rowIds, columnIds }`): the selection in
  stable `CellRef` terms: the `onSelectionChange` payload, the `selection`/`defaultSelection`
  prop value, and the `setSelection`/`getSelection` arguments. The active cell is deliberately
  not part of it. See
  [Events & state](/docs/events-state#2-onselectionchange).
- `ViewCoord` (`{ col, row }`): view-index: the sorted/filtered row position, not a `data`
  index. It moves when the view changes.
- `ViewCellRef` (`{ rowId, columnId, viewRowIndex, viewColumnIndex }`): a `CellRef` plus the
  view position the cell occupied when an event fired. `onActiveCellChange`, `onEditStart`, and
  `onEditEnd` deliver it.
- `GridRect` (`{ x, y, width, height }`, half-open).
- `GridSelection` (`{ current: {cell, range, rangeStack} | null, rows, columns }`).
- `DataOp<TData>` (`update`, `insert`, `delete`, or `move`, row-id-based) and `DataChange<TData>`
  (`{ ops, source }`).
- `SortSpec` (`{ columnId, direction }`), `FilterSpec`, and `FilterOperator`.
- `CellTypeFilter` (`{ operators?, match?, valueInput? }`),
  `CellTypeValueInput` (`"text" | "number" | "date" | "boolean" | "choices"`), and
  `FilterValueInputProps` (the props of a custom `valueInput` component), the filter
  capabilities a cell type declares. See
  [custom cell types](/docs/custom-cell-types#the-contract-member-by-member).
- `GridActions` (the named keyboard actions, as an interface you can extend by declaration
  merging) and `GridAction` (every named keyboard action, the built-ins plus any you merged in)
  and `Keymap` (`Partial<Record<GridAction, KeyBinding[]>>`).
- `GridCommand<TData>` (`{ run, when?, scope?, label?, group? }`) and `GridCommandCtx<TData>`
  (`{ api, cell, viewRowIndex, viewColumnIndex, row, readOnly }`): the custom-command contract
  behind the `commands` prop. `scope` selects when the command dispatches (`"grid"`,
  `"editing"`, `"always"`), and `CommandGroup` names the keybindings dialog's sections. See
  [Keybindings: Custom commands](/docs/addons/keybindings#custom-commands).
- `RowMarkersMode`, `HeaderClickBehavior`, and `DensityMode`.
- `ColumnLayout` (`{ widths, order, pins, hidden }`): the full layout snapshot: the
  `onColumnLayoutChange` payload, and the shape of the `columnLayout`/`defaultColumnLayout`
  props in `Partial` form. See
  [Events & state](/docs/events-state#8-columnlayout--defaultcolumnlayout--oncolumnlayoutchange--oncolumnresizing).
- `DataGridPlugin<TData>` (`{ name, Overlay?, rowBands?, onDataChange?, commands?, keymap?, Mount? }`),
  `PluginRowBands` (`{ top?, bottom?, render }`), `RowBandRenderCtx`, `DataGridPluginCtx<TData>`
  (`{ api }`), and `OverlayPluginCtx`: the plugin members and their contexts. See
  [Plugins](/docs/plugins) for the full contract and a worked example, and
  [Multiplayer presence](/docs/addons/presence), [Fill handle](/docs/addons/fill),
  [Undo & redo](/docs/addons/undo-redo), and [Pinned rows](/docs/addons/pinned-rows) for the
  first-party consumers.
- `CellErrorEntry` (`{ rowId, columnId, message }`) and `CellErrorTarget` (`{ rowId, columnId }`),
  the input shapes for `actions.setCellErrors`/`actions.clearCellErrors`. See
  [Editing & cell types: Server errors](/docs/editing-cell-types#server-errors).
- `GridEditEndEvent` (`{ rowId, columnId, viewRowIndex, viewColumnIndex, result: "commit" | "cancel" | "rejected" }`),
  `GridValidationErrorEvent` (`{ source: "paste" | "fill", rejected }`), and
  `GridBulkValidationError` (`{ rowId, columnId, viewRowIndex, value, message }`), the payloads of
  `onEditEnd` and `onValidationError`. See
  [Events & state](/docs/events-state#10-edit-lifecycle-and-cell-events).

`createFilterMatcher(filter)` pre-parses the bounds of a `FilterSpec` once
and returns a reusable `(text: string) => boolean` matcher. This has the same semantics as
`matchesFilter`, but without re-parsing the filter's value on every row.

## Operation engine

## Op engine <NewBadge />

The core applies every `DataChange` batch through one engine. The `data-grid` barrel exports it
for consumers who apply operations to their own copy of the data:

- **`applyChange(data, change, getRowId)`**: applies a batch to a row array and returns a new
  array, in O(n + k log(n + k)) for `n` rows and `k` operations. A `move` operation applies as a delete plus
  an insert at `to`.
- **Row-id-based, missing-id skip.** `update` and `delete` operations locate the row by `rowId`, never by
  the operation's stored index. If the row id is no longer present, that operation is skipped, not an error.
- **Snapshot indices.** Each operation's `index` is the row's position in the array as it stood before
  the whole batch, not a running position updated one operation at a time. `insert` operations apply in ascending
  index order, so a multi-row batch round-trips through `invertChange`.
- **`invertChange(change)`**: returns the change that undoes a batch. Each operation is inverted:
  `update` swaps `row`/`prev`, `insert` becomes `delete` and back, `move` swaps `from`/`to`.
  The operation order is reversed, so a batch unwinds in the correct dependency order.

The grid's `onDataChange` and the `data-grid-history` add-on run this same engine. A consumer
cache that applies operations with `applyChange` stays in step with the grid and with undo.
