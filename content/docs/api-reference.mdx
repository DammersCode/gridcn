### `store`: external store ownership

By default `DataGridProvider` creates and owns its store. When logic OUTSIDE the provider's
subtree needs the grid imperatively — an `onDataChange` handler talking to a server, a WebSocket
push of validation errors, a page-level control — create the store yourself with
`useDataGridStoreProps(props)` and feed it in through the `store` prop (on both
`DataGridProvider` and `DataGrid`):

```tsx
const { store, actions } = useDataGridStoreProps({ data, columns, getRowId, onDataChange: handleDataChange });

function handleDataChange(next: readonly Order[], change: DataChange<Order>) {
  setData(next);
  saveOrders(change.ops).catch((error) => {
    actions.setCellErrors(parseFieldErrors(error)); // stable object — no ref, no null check
  });
}

return <DataGrid store={store} data={data} columns={columns} getRowId={getRowId} onDataChange={handleDataChange} />;
```

- `useDataGridStoreProps` takes the same sync props as the provider and keeps the store in sync
  with them on every render — pass it the same live props the grid renders from.
- `actions` is stable for the store's lifetime and available on the first render, so a closure
  can capture it directly.
- With `store` set, the provider is a pure context shell: it creates nothing, syncs nothing, and
  subscribes to nothing — your `useDataGridStoreProps` call owns the store.
- `store.getState()` and `store.subscribe()` are reachable from outside React for anything the
  selector hooks can't reach, e.g. a page-level error badge that renders outside the provider.

### `overlayPlugins`

`readonly OverlayPlugin[]`, optional, on both `DataGridProvider` and `DataGrid`. Each registered
plugin paints into the same overlay layer the core's own selection and active-cell rendering use.
See [Overlay plugins](/docs/overlay-plugins) for the full contract, and
[Multiplayer presence](/docs/addons/presence) and [Fill handle](/docs/addons/fill) for two
first-party consumers.

<Callout type="warn" title="Pass a stable array reference">
  A dev-mode guardrail warns when the `overlayPlugins` array's identity changes across renders:
  `"overlayPlugins array identity changed since the last render; pass a stable reference (module
  scope or useMemo) or DataGridOverlays re-renders every tick"`. Memoize the array itself, not
  only the plugin functions inside it: `useMemo(() => [plugin], [plugin])`, not a fresh `[plugin]`
  literal written inline on every render of your own component.
</Callout>

### Hooks

State access is hooks only. Call them under `DataGridProvider`; the one way out is
`useDataGridStoreProps` (above), which hands you the store itself for code outside the
provider's subtree. The full list lives in `store/hooks.ts`. These are the ones you will reach
for most:

- `useDataGridActions()` — the single stable actions object (`setSorts`, `setFilters`,
  `setSearch`, `setColumnWidth`, `setColumnOrder`, `setColumnPin`, `setColumnHidden`,
  `selectCell`, `extendTo`, `startEditing`, `commitCellEdit`, `deleteSelection`, `updateCells`,
  `updateRows`, `reconcileView`, `setCellErrors`, `clearCellErrors`, plus the row operations
  `insertRow`, `duplicateRows`, `deleteRows` — see [Row operations](/docs/row-operations)). The
  complete list is the `DataGridActions` type.
- `useDataGridViewStale()` — true when a write left the sorted order stale: a deferred
  `updateCells` batch, or an edit, paste, fill, or cleared selection that touched a column the
  active sort or filter reads. See [Streaming updates](/docs/streaming-updates).
- `useDataGridCellTypes()` — the resolved cell-type registry (built-ins or consumer-provided),
  for tooling that needs to inspect or resolve a column's renderer/editor.
- `useDataGridActiveColumn()` — the active cell's column index (or `null`), for tooling that only
  cares about the active column.
- `useDataGridActiveCell()`, `useDataGridSelection()`, `useDataGridGetSelectionValues()`, `useDataGridEditing()`
- `useDataGridSortState()`, `useDataGridFilterState()`, `useDataGridSearchText()`
- `useDataGridVisibleColumns()`, `useDataGridAllColumns()`, `useDataGridColumnWidth(id)`,
  `useDataGridIsColumnHidden(id)`
- `useDataGridLabels()`, `useDataGridKeymap()`, `useDataGridReadOnly()`
- `useDataGridScrollToCell()` — imperative scroll.
- `useDataGridCellErrors()` — the full post-commit server-error map. See
  [Editing & cell types: Server errors](/docs/editing-cell-types#server-errors).

`onSelectionChange`, `onColumnLayoutChange`, and every other event source are covered in full on
[Events & state](/docs/events-state).

## `ColumnDef<TData, TValue>`

<AutoTypeTable path="./registry/default/blocks/data-grid/types.ts" name="ColumnDef" />

<Callout title="Prefer defineColumns over typing ColumnDef[] by hand">
  `defineColumns<TData>()([...])` infers `TValue` per column from `accessorKey` or `accessorFn`,
  and narrows `options` and `validate` through the cell type's key in `GridCellTypes`, catching
  column-id typos and type-key typos at compile time. See
  [Quick start](/docs/quick-start#define-columns).
</Callout>

`AnyColumnDef` (`ColumnDef<unknown, unknown, any>`) is the row-agnostic shape that the store and
its hooks (`useDataGridVisibleColumns()`, `useDataGridAllColumns()`, and similar hooks) actually
traffic in. Reach for it when you write custom column UI that does not know its `TData` generic.

<Callout title="validate's type: a union, and a 3rd type parameter">
  `validate` is `((value: TValue, row: TData) => string | null) | StandardSchemaV1<TValue>`: the
  function form, or any [Standard Schema](https://standardschema.dev). `ColumnDef` has a 3rd type
  parameter, `TValidate` (defaults to `TValue`), because the function-or-schema union does not
  stay assignable when the row-agnostic `AnyColumnDef` erases its type parameters to `unknown` —
  so `AnyColumnDef` erases `TValidate` to `any` instead. This never affects how you author
  `validate` on a concretely-typed column through `defineColumns`. `StandardSchemaV1.InferInput<S>`
  and `InferOutput<S>` are exported from `types.ts` for inspecting a schema's own input and output
  types.
</Callout>

## `CellType<TData, TValue, TOptions>`

<AutoTypeTable path="./registry/default/blocks/data-grid/types.ts" name="CellType" />

Register custom types through the `cellTypes` prop of `DataGridProvider`. A provided registry
REPLACES the built-ins (`text`, `number`, `checkbox`, `select`, `date`) rather than merging over
them: to extend the built-ins, spread the exported `cellTypes` in
(`cellTypes={{ ...cellTypes, myType }}`). See
[Recipes](/docs/recipes#custom-cell-type) for a worked example.

### `GridCellTypes`

This interface map gives `defineColumns` its per-type inference. Augment it through declaration
merging in your own module to give a custom cell type the same compile-time `options` and value
narrowing as the built-ins:

```ts
declare module "@/components/data-grid/types" {
  interface GridCellTypes {
    currency: { value: number | null; options: { currency: string } };
  }
}
```

Adjust the module path to wherever your `components.json` aliases actually placed `types.ts`.

## Other exported types

- `CellCoord` (`{ col, row }`, data-space) and `GridRect` (`{ x, y, width, height }`, half-open).
- `GridSelection` (`{ current: {cell, range, rangeStack} | null, rows, columns }`).
- `DataOp<TData>` (`update`, `insert`, or `delete`, id-keyed) and `DataChange<TData>`
  (`{ ops, source }`).
- `SortSpec` (`{ columnId, direction }`), `FilterSpec`, and `FilterOperator`.
- `GridAction` (every named keyboard action) and `Keymap`
  (`Partial<Record<GridAction, string[]>>`).
- `RowMarkersMode`, `HeaderClickBehavior`, and `DensityMode`.
- `ColumnLayout` (`{ widths, order, pins, hidden }`), the `defaultColumnLayout` and
  `onColumnLayoutChange` snapshot. See
  [Events & state](/docs/events-state#8-oncolumnlayoutchange--defaultcolumnlayout--oncolumnresizing).
- `OverlayPlugin` (`(ctx: OverlayPluginCtx) => ReactNode`) and `OverlayPluginCtx`, the
  overlay-plugin seam that add-ons like `data-grid-presence` and `data-grid-fill` register into.
  See [Overlay plugins](/docs/overlay-plugins) for the full contract and a worked example, and
  [Multiplayer presence](/docs/addons/presence) and [Fill handle](/docs/addons/fill) for two
  first-party consumers.

  <AutoTypeTable path="./registry/default/blocks/data-grid/overlays.tsx" name="OverlayPluginCtx" />

- `RowBandsSpec` and `RowBandRenderCtx`, the provider-level row-bands seam that
  `data-grid-pinned-rows` registers into. See [Pinned rows](/docs/addons/pinned-rows).
- `CellErrorEntry` (`{ rowId, columnId, message }`) and `CellErrorTarget` (`{ rowId, columnId }`),
  the input shapes for `actions.setCellErrors`/`actions.clearCellErrors`. See
  [Editing & cell types: Server errors](/docs/editing-cell-types#server-errors).

`createFilterMatcher(filter)` (from `sort-filter`) pre-parses the bounds of a `FilterSpec` once
and returns a reusable `(text: string) => boolean` matcher. This has the same semantics as
`matchesFilter`, but without re-parsing the filter's value on every row.
