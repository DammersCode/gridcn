## Initial fetch

Go controlled (see [Quick start](/docs/quick-start#going-controlled)). Fetch once, then hold
`data` in state:

```tsx
"use client";

function OrdersGrid() {
  const [data, setData] = useState<Order[]>([]);

  useEffect(() => {
    let cancelled = false;
    api.orders.list().then((rows) => {
      if (!cancelled) setData(rows);
    });
    return () => {
      cancelled = true;
    };
  }, []);

  return (
    <DataGrid
      data={data}
      columns={columns}
      onDataChange={setData}
      onSave={save}
    />
  );
}
```

## Translate operations into API calls

`change.ops` is an array of `DataOp<Order>`. Each operation names its own shape, so a `switch` on
`op.type` maps to one API call per operation. The `move` operations of a batch go in one request:

```ts
function opsToRequests(ops: DataOp<Order>[]) {
  const requests = ops.flatMap((op) => {
    switch (op.type) {
      case "update":
        // op.cells is present for a cell edit/paste/fill; absent for a whole-row update.
        // Send a patch keyed by rowId, not an index — indices don't survive sort or filter.
        return [api.orders.patch(op.rowId, op.cells ? cellsToPatch(op.cells) : op.row)];
      case "insert":
        return [api.orders.create(op.row)];
      case "delete":
        return [api.orders.remove(op.rowId)];
      case "move":
        return [];
    }
  });
  const moves = ops.filter((op) => op.type === "move");
  if (moves.length > 0) requests.push(api.orders.reorder(moves.map(({ rowId, to }) => ({ rowId, to }))));
  return requests;
}

type UpdateOp<TData> = Extract<DataOp<TData>, { type: "update" }>;

function cellsToPatch(cells: NonNullable<UpdateOp<Order>["cells"]>) {
  return Object.fromEntries(cells.map((cell) => [cell.columnId, cell.value]));
}
```

Each move's `to` is the row's final index after the whole batch. The server removes all moved rows,
then inserts them in ascending `to` order, as `applyChange` does. Moves applied one at a time end
in the wrong order.

## Strategy A: optimistic, roll back on failure

Keep `data` in your state and apply every change at once with `onDataChange`. Send the change from `onSave`. If the returned promise rejects, the grid reverts the whole change:

```tsx
async function save(change: DataChange<Order>) {
  try {
    await Promise.all(opsToRequests(change.ops));
  } catch (error) {
    toast.error("Could not save your change. It has been reverted.");
    reportError(error);
    throw error;
  }
}

<DataGrid data={data} onDataChange={setData} onSave={save} /* other props */ />
```

`onSave` never receives a rollback, stream, or history change, so a revert never goes back to the server.

## Strategy B: refetch-on-settle

Send the change from `onSave`, then replace `data` with a fresh fetch once the server confirms the write. Pick it when the server recomputes values:

```tsx
async function save(change: DataChange<Order>) {
  await Promise.all(opsToRequests(change.ops));
  setData(await api.orders.list());
}

<DataGrid data={data} onDataChange={setData} onSave={save} /* other props */ />
```

<Callout type="idea" title="Optimistic vs refetch-on-settle">
  Both send the change from `onSave`. Optimistic leaves `data` as the grid wrote it. Refetch-on-settle
  replaces it with server-confirmed data after the round-trip. Use refetch-on-settle for edits a
  server can recompute (a price that triggers server-side discounts).
</Callout>

## Strategy C: acknowledge each change

<NewBadge />

`onDataChange` keeps your state in step with the grid. `onSave` sends the change to the server and answers with the rows the server refused. The grid marks the rows `saving`, reverts only the refused ones, and keeps everything the server accepted:

```ts
const onSave = async (change: DataChange<Order>): Promise<WriteAck<Order>> => {
  const results = await Promise.allSettled(opsToRequests(change.ops));
  return { rejected: refusedRows(change.ops, results) };
};

function refusedRows(ops: DataOp<Order>[], results: PromiseSettledResult<unknown>[]): WriteRejection<Order>[] {
  // Map each failed request back to its row. Pass the row the server holds as `current` when you have it.
  return results.flatMap((result, i) =>
    result.status === "rejected" ? [{ rowId: ops[i]!.rowId, message: String(result.reason) }] : [],
  );
}

<DataGridProvider
  data={data}
  onDataChange={(next) => setData(next as Order[])}
  onSave={onSave}
  onWriteRejected={({ rejected }) => toast.error(rejected[0]?.message ?? "Refused")}
  {...grid}
/>
```

<ComponentPreview name="data-grid-write-ack-demo" />

- `onDataChange` carries every change of `data` once, the revert of a refusal included. It returns nothing. `onSave` is the only place that returns an acknowledgement.
- `onSave` never receives a change with `source: "rollback"`, so a revert never goes back to the server. It never receives `source: "stream"` either: a server push must not echo back.
- A promise that resolves with nothing accepts the whole change. A promise that rejects, or a handler that throws, refuses the whole change.
- `rejected` entries name a `rowId`, and optionally a `columnId` to refuse one cell of an update. The grid reverts a cell only while it still holds the refused value, so a newer edit to the same cell survives.
- `current` is the row as the server holds it now. The revert puts it in place of the refused row, unless a newer write to the row is pending or has already settled. A refused move still reverts its position. If `getRowId(current)` throws or differs from `rowId`, the grid ignores `current`. A refused delete restores `current`. A refused insert removes the row. The grid warns once in development when it ignores `current`.
- While the promise is pending, the row element carries `data-write-status="saving"`. After a refusal it carries `failed` until the next write to the row or `actions.clearWriteStatus()`. `useDataGridRowWriteStatus(rowId)` and `useDataGridPendingWriteCount()` read the same state.
- The revert is one `onDataChange` call with `source: "rollback"` and `reverts` set to the refused change. The cell errors of the reverted cells clear in the same step. `useDataGridHistory` drops the undone entry.
- `onWriteRejected({ change, rejected })` runs once per refused change, after the revert. Show the server's `message` there.
- A `readOnly` grid skips the revert and `current`, warns once in development, and still calls `onWriteRejected`.
- A refusal that arrives after the data was replaced (a page change) re-inserts a refused delete into the new data. Reload the page in `onWriteRejected` when that matters.
- The callbacks run after the outermost write in this order: `onDataChange`, `onSave`, plugin observers. A throw in one does not stop the next.

Strategy C does not roll back a change of `change.ops` that the server accepted, which Strategy A does when one request of a batch fails. It needs no `ref` snapshot.

## The failure path

A rejected write is common: a 422 with field-level errors is the typical shape from a REST or
GraphQL backend. `actions.setCellErrors` (on the grid's `ref` handle) paints the rejection on the exact cell it names, so the
user sees which value is wrong and can fix it in place:

```ts
async function save(change: DataChange<Order>, gridRef: RefObject<DataGridApi<Order> | null>) {
  try {
    await Promise.all(opsToRequests(change.ops));
  } catch (error) {
    gridRef.current?.actions.setCellErrors(parseFieldErrors(error, change.ops)); // [{ rowId, columnId, message }]
  }
}
```

`parseFieldErrors` is your own mapping from the server's error shape to `{ rowId, columnId,
message }` entries, matched against `change.ops` to recover each op's `rowId`. The cell gets the
same ring, tint, and `aria-invalid` treatment as a rejected `validate` call, and the message shows
when the user opens the cell to edit it. The error clears the moment the user commits a fixed
value, through any write path. See
[Editing & cell types: Server errors](/docs/editing-cell-types#server-errors) for the full
contract, including `clearCellErrors` and the read hook.

<Callout type="idea" title="Toast and revert, or history undo, still apply">
  `setCellErrors` does not roll back the value on its own. Pair it with
  [Strategy A](#strategy-a-optimistic-roll-back-on-failure)'s rollback, or
  [`data-grid-history`](/docs/addons/undo-redo)'s `undo()`, when leaving the rejected
  value showing is the wrong choice.
</Callout>
