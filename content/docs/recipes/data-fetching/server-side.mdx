A server grid shows the rows your backend returns. The grid tracks what the user chose, which is
the *spec*: sort, filter, search, and page. You send the spec to your API. The response becomes
`data`. Two root props, `sortMode="server"` and `filterMode="server"`, stop the grid from
sorting and filtering the response a second time.

## One hook for pages

<NewBadge />

For a paged grid, `useDataGridServerRows` does steps 1 to 4 below and the race guard. It returns `gridProps`, `pager`, `error`, `retry`, and `refresh`. See [Server side](/docs/examples/data/server-side).

## The contract

1. Set `sortMode="server"` and `filterMode="server"` on the provider. Set them at mount, so a spec restored at mount never sorts or filters on the client.
2. Read the spec from the grid. Use the store hooks (`useDataGridSortState`,
   `useDataGridFilterState`) or the controlled pairs (`sortState` and `onSortChange`).
3. Send the spec to your API. Make one request for each view state.
4. Pass the response as `data`. Pass `total` to the pager or to `useDataGridLazyRows`, and pass the same count to the provider as `totalRowCount` (`null` when the server sends none).

Set `headerClickBehavior="sort"`. The default, `"select"`, makes a header click select the column,
and `onSortChange` never fires.

## Sort

The grid shows the sort indicator and `aria-sort`, and it calls `onSortChange`. It never reorders
`data`. The order of your response is the displayed order. Refetch when the spec changes:

```tsx
<DataGridProvider
  data={rows}
  columns={columns}
  getRowId={(row) => row.id}
  sortMode="server"
  filterMode="server"
  headerClickBehavior="sort"
  onSortChange={setSorts}
  onFilterChange={setFilters}
>
  {/* toolbar, header, body */}
</DataGridProvider>
```

An edit to a sorted column shows no re-sort hint under `sortMode="server"`. Refetch to get the
new order.

## Filter

The grid tracks the filter tree: the filter menu, the header filters, and the `data-filtered`
indicator all show it. It never removes rows from `data`. Your backend applies the tree, and the
response holds the matching rows. The tree is untrusted input. Check its depth, size, and column
names before you build a query (the [ORM recipes](/docs/examples/data/orm) show the check).

The header filter popover and the `isAnyOf` input of the filter menu list the values of the
loaded rows. Pass `fetchFilterValues` to list the values of the whole column from your backend. See
[Server values](/docs/addons/toolbar#server-values).

## Search

The quick-search box highlights and navigates matches in the loaded rows. It never narrows the
view, in any mode. To search the whole dataset, send `searchText` to your fetch. Read it with
`useDataGridSearchText`, or use the `searchText` and `onSearchTextChange` pair. Your response
holds the matching rows, and the box then highlights them.

## Pagination or lazy rows

Both sources take the same spec. They differ in how rows reach the grid.

| | [Pagination](/docs/pagination#server-mode) | [Lazy loading](/docs/lazy-loading) |
|---|---|---|
| The grid shows | One page at a time | One continuous list of `total` rows |
| You send | `page`, `pageSize`, and the spec | `start`, `end`, and the spec |
| The response holds | The rows of one page and the filtered `total` | The rows of one window |
| After a spec change | Go to page 1 and refetch | Reset the loaded rows and refetch |
| Stale responses | Ignore a response for an old request | `fetchRows` receives an `AbortSignal` |

Set `total` to the filtered count on each filter change. When `total` shrinks, the pager shows a
clamped page, but your `page` state changes only with `reconcilePage: true`
([Server mode](/docs/pagination#server-mode)). With lazy rows, a changed `total` resets the hook and drops every fetched window. Call
`lazy.reset()` when `total` stays the same. See
[Sorting a lazy grid](/docs/lazy-loading#sorting-a-lazy-grid) and
[Filtering a lazy grid](/docs/lazy-loading#filtering-a-lazy-grid).

The cell range and the active cell follow their row ids while the rows stay in `data`. A page
change or refetch that removes a row drops it from the range. Checked rows depend on `totalRowCount`:
without it, a checked row that leaves `data` drops out. With it (and `keepCheckedRows`), the grid
remembers the check by row id and checks the row again when it returns. See
[Selection and bulk actions](#selection-and-bulk-actions).

## Row count and unknown totals

<NewBadge />

Pass the filtered row count to the provider as `totalRowCount`. It sizes the "select all" count and
marks `data` as a window of a larger result. A server that sends no count has two connections:

- Pages: `useDataGridPagination({ page, pageSize, hasNextPage, onPageChange })`. The footer shows
  "Page N" and enables Next while `hasNextPage` is true. See [Pagination](/docs/pagination#without-a-total).
- Scroll: `useDataGridInfiniteRows` loads a cursor chain and grows the list in steps. See
  [A source with no total](/docs/lazy-loading#a-source-with-no-total). Pass `totalRowCount={null}`.

## Selection and bulk actions

<NewBadge />

Set `keepCheckedRows` and `totalRowCount` (`useDataGridServerRows` sets both). Checks then survive page changes, evictions, and server sort
or filter changes, and `actions.selectAllMatching()` selects the whole result:

```tsx
const selected = useDataGridSelectedRows();
await api.deleteOrders(selected.mode === "ids" ? { ids: selected.ids } : { filters, search, exceptIds: selected.excludedIds });
```

Send the spec you already hold with the ids. The server evaluates and bounds both. See
[Selection over a server result](/docs/selection-keyboard#selection-over-a-server-result).

## Saving and refusals

<NewBadge />

Send an edit to your API from `onSave(change)`. Return a promise that resolves with the rows the server
refused. The grid marks the rows `saving`, reverts only the refused ones, and calls `onSaveRejected`:

```tsx
<DataGridProvider
  onDataChange={(next) => setRows(next as Order[])}
  onSave={async (change) => ({ rejected: await api.saveOrders(change.ops) })}
  onSaveRejected={({ rejected }) => toast.error(rejected[0]?.message ?? "Refused")}
/>
```

`onSave` never receives the revert (`source: "rollback"`) or a server push (`source: "stream"`). See
[Server round-trip](/docs/recipes/data-fetching/server-round-trip#strategy-c-acknowledge-each-change)
and [TanStack Query](/docs/recipes/data-fetching/tanstack-query).

## Async gates

[Async gates](/docs/examples/validation/async-gates) hold a paste, an edit start, or a row insert
until your API answers. The grid drops the result of a gate, with no error, when:

- the grid is `readOnly`,
- the target row is no longer in `data`, for example after a refetch removed it,
- the sort or filter spec changes during a pending paste.

A gate gets no `AbortSignal`. Show a busy state while a gate is pending. The grid ignores a
second paste, edit start, or insert until the first one settles.

`validateRow` runs after the write commits, and its verdict sets the row errors.

## Races and row identity

When the spec changes twice fast, the older response can arrive last. Cancel the first request,
or ignore the older response:

```tsx
useEffect(() => {
  let stale = false;
  api.rows({ sorts, filters, searchText }).then((res) => {
    if (!stale) setRows(res.rows);
  });
  return () => {
    stale = true;
  };
}, [sorts, filters, searchText]);
```

Keep `getRowId` stable across fetches. Selection, edit state, and row operations follow row ids.

## URL state

[`DataGridUrlState`](/docs/addons/url-state) writes the spec from the URL into the grid store on
mount. With both modes set to `"server"`, the store keeps the spec and never sorts or filters the
response. Your fetch reads the restored spec and loads the rows. With pagination, add
`useDataGridUrlPagination` for `page` and `pageSize`.

<Callout type="warn">
  Without both modes set to `"server"`, a URL-restored spec sorts and filters partial data in the
  browser. The result is wrong, and the grid shows no error.
</Callout>
