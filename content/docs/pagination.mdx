`data-grid-pagination` is a UX and server-load pattern, not a performance need.

`defaultPageSize` on `DataGridProvider` pages the view: the grid keeps all of `data`, sorts and filters all of it, and shows one page of the result. `<DataGridPaginationBar />` renders the footer, composed from parts in the
shadcn-`Pagination` style. For rows your server pages, `useDataGridServerPager` builds the pager. Virtualization already handles rendering huge datasets cheaply either
way, so neither exists for rendering performance, and using this add-on with lazy loading is not supported. When to pick which is on the
[Lazy loading](/docs/lazy-loading) page.

    ## Client mode <NewBadge />

    Set `defaultPageSize` on the provider and render the bar inside it. The bar reads the pager from the grid:

    ```tsx
    "use client";

    import { DataGridProvider, DataGridRoot, DataGridHeader, DataGridBody } from "@/components/data-grid/data-grid";
    import { DataGridPaginationBar } from "@/components/data-grid-pagination/data-grid-pagination";

    function OrdersGrid({ rows }: { rows: Order[] }) {
      return (
        <DataGridProvider data={rows} columns={columns} getRowId={(row) => row.id} defaultPageSize={25} headerClickBehavior="sort">
          <DataGridRoot>
            <DataGridHeader />
            <DataGridBody />
          </DataGridRoot>
          <DataGridPaginationBar />
        </DataGridProvider>
      );
    }
    ```

    - A sort orders every row. A filter narrows every row, and the footer counts the rows that remain. A filter change goes back to page 1.
    - `onDataChange` receives the whole array, so a setter can take it as is.
    - A pinned totals band and a streaming `updateCells` batch cover every row, not one page.
    - A page change keeps the checked rows, the cell range, and the active cell that stay on screen, and drops the rest.
    - Quick search marks the matches on the current page. Use the filter menu to search every page.
    - `exportGrid`, `printGrid`, and `useDataGridAggregate` cover every page; pass `scope: "page"` for the shown page only. `actions.setPageSize(null)` shows every row again.
    - The page is `defaultPage` (seed) or `page` with `onPageChange` (controlled). `pageSize` with `onPageSizeChange` controls the size. A page past the last one shows the last. `useDataGridPager()` returns the same controls for a footer of your own.

    `useDataGridPagination({ data })` still slices an array into pages for a list outside the grid, with `pageData` and `pager`.

    ## Server mode

    `useDataGridServerPager({ page, pageSize, totalRowCount, onPageChange })` is fully controlled. You own the page index and
    fetch each page's rows yourself. The hook only computes `pageCount` and page-window math, so
    `<DataGridPaginationBar {...pager} />` renders identically either way. `useDataGridServerRows` does all of this for you, including the request, the race guard, and the reset to page 1:

    ```tsx
    "use client";

    import { useEffect, useState } from "react";
    import { DataGrid, defineColumns, type FilterNode } from "@/components/data-grid/data-grid";
    import { useDataGridServerPager, DataGridPaginationBar } from "@/components/data-grid-pagination/data-grid-pagination";

    function OrdersGrid() {
      const [page, setPage] = useState(1);
      const [pageSize, setPageSize] = useState(25);
      const [filters, setFilters] = useState<FilterNode[]>([]);
      const [rows, setRows] = useState<Order[]>([]);
      const [total, setTotal] = useState(0);

      useEffect(() => {
        // Guard against stale responses: a page-2 answer arriving after page-3's request
        // must not overwrite page-3's rows (fast page clicks race the network).
        let stale = false;
        api.orders({ page, pageSize, filters }).then((res) => {
          if (stale) return;
          setRows(res.rows);
          setTotal(res.total);
        });
        return () => { stale = true; };
      }, [page, pageSize, filters]);

      const { pager } = useDataGridServerPager({
        page,
        pageSize,
        totalRowCount: total,
        onPageChange: setPage,
        onPageSizeChange: setPageSize,
      });

      return (
        <>
          <DataGrid
            data={rows}
            columns={columns}
            getRowId={(row) => row.id}
            filterMode="server"
            onFilterChange={(next) => {
              setFilters(next);
              setPage(1);
            }}
          />
          <DataGridPaginationBar {...pager} />
        </>
      );
    }
    ```

    <NewBadge />

    For the full contract, see [Server-side data](/docs/recipes/data-fetching/server-side).

    `filterMode="server"` keeps the grid from filtering the fetched page again. The filter spec goes
    to your server with the page, and the server returns the filtered count. A filter change moves
    back to page 1.

    ### Without a total

    <NewBadge />

    A keyset or "has more" API returns a page and a flag, not a count. Pass `totalRowCount: null` with
    `hasMore`:

    ```tsx
    const { pager } = useDataGridServerPager({ page, pageSize, totalRowCount: null, hasMore, onPageChange: setPage });
    ```

    The pager then reports `totalRowCount: null`. The footer shows "Page 3" instead of a range, enables
    Next while `hasMore` is `true`, and disables Last. The numbered buttons reach one page past
    the current one. The hook lifts a page below 1 and never clamps the upper end.

    <ComponentPreview name="data-grid-open-ended-demo" />

    `useDataGridServerRows` keeps the cursor chain for you. <NewBadge /> Return `nextCursor` from `fetchRows`
    and read `cursor` from the request:

    ```tsx
    const server = useDataGridServerRows<Order, string>({
      getRowId: (row) => row.id,
      fetchRows: async ({ cursor, pageSize, spec, signal }) => {
        const res = await api.orders({ after: cursor, limit: pageSize, spec, signal });
        return { rows: res.items, nextCursor: res.next ?? null };
      },
    });
    ```

    - Page 1 gets `cursor: undefined`. The hook stores the `nextCursor` of page `p` as the cursor of page `p + 1`. `nextCursor: null` ends the source.
    - A change of the sort, filter, search text, or page size drops the chain and goes back to page 1.
    - Back, forward, `refresh()`, and `retry()` reuse the stored cursors.
    - The pager shows the pages up to one past the current page, and no count or last page. A page whose cursor is known is reachable. A cursor source starts at page 1; a `defaultPage` or URL page beyond the chain moves back. A `page` beyond the chain moves back to the furthest known page through `onPageChange`.

    With React Query or SWR, the library owns the cache and the chain. Pass `hasMore` to `useDataGridServerPager` and
    fetch the next page before you move to it:

    <ComponentPreview name="data-grid-cursor-swr-demo" />

    Checked rows survive a page change once `totalRowCount={pager.totalRowCount}` is set. Add
    `keepCheckedRows` to act on them. Select every matching row with `actions.selectAllMatching()`. See
    [Selection over a server result](/docs/selection-keyboard#selection-over-a-server-result).

    When `totalRowCount` shrinks below `page`, the hook calls your `onPageChange` <NewBadge /> once with the
    clamped page. The hook never sets your state. While `totalRowCount` is `0` (your first fetch is
    still in flight), the hook keeps your page, so a deep link survives until the count arrives.

    Without `onPageSizeChange`, the bar hides the page-size select.

    ## `<DataGridPaginationBar />`

    The default footer has:

    - First and prev buttons.
    - A sliding set of page-number buttons (5 at a time by default, sliding to stay centered on
      the current page; the bar's `windowSize` prop changes the count).
    - Next and last buttons.
    - A page-size `<Select>`.
    - An "x-y of z" range label.

    Inside `DataGridProvider` with no controls spread, it reads the pager from the grid. Spread
    `{...pager}` from `useDataGridServerPager` or `useDataGridServerRows` and it works inside or outside the provider. All strings route through the
    `labels.pagination` group (see [i18n](/docs/i18n#coverage-by-group)). Pass a `labels` prop
    directly on `<DataGridPaginationBar>` to override them.

    | Prop | Type | Meaning |
    |---|---|---|
    | `className` | `string` | Merged onto the footer's root `<div>` after the built-in classes. A conflicting utility wins. |
    | `labels` | `Partial<DataGridPaginationLabels>` | Deep-merged override of the `labels.pagination` group, same merge semantics as core's `labels` prop. |
    | `windowSize` | `number` | How many numbered page buttons the default layout shows at once (default 5). Ignored with `children`. |

    The root `<div>` also carries `[data-grid-pagination]`, for CSS that targets the footer without
    a `className` (see [Data-attribute contract](/docs/styling-theming#data-attribute-contract)).

    ## Composition

    `DataGridPaginationBar` renders its default layout only when given no `children`. Pass
    `children` built from the parts below for a custom arrangement, for example a compact bar with
    only first, prev, next, and last, and no page numbers:

    ```tsx
    <DataGridPaginationBar {...pager}>
      <DataGridPaginationRange />
      <div className="flex items-center gap-1">
        <DataGridPaginationFirst />
        <DataGridPaginationPrev />
        <DataGridPaginationNext />
        <DataGridPaginationLast />
      </div>
    </DataGridPaginationBar>
    ```

    Every part reads the bar's controls and labels through context, so none of them take the
    pagination props directly. Only `DataGridPaginationBar` does. Each part throws if rendered
    outside a `DataGridPaginationBar`.

    - `DataGridPaginationRange`: the "x-y of z" label.
    - `DataGridPaginationPageSize`: the rows-per-page `<Select>`.
    - `DataGridPaginationFirst` / `DataGridPaginationLast`: jump to page 1 or the last page.
      Disabled at their respective edge.
    - `DataGridPaginationPrev` / `DataGridPaginationNext`: moves the page by 1, chevron-only.
      Disabled at their respective edge.
    - `DataGridPaginationPages`: the sliding numbered page buttons, the only source of page
      numbers. Takes an optional `windowSize` prop (default 5).

## Composing with `data-grid-url-state`

`useDataGridUrlPagination` (from `data-grid-url-state`) syncs `page` and `pageSize` with the URL
via nuqs. It hands back the controlled pair that `DataGridProvider` (client mode) and `useDataGridServerPager` (server mode) both accept, so either composes with one spread:

```tsx
"use client";

import { useDataGridUrlPagination } from "@/components/data-grid-url-state/data-grid-url-state";
import { DataGridProvider, DataGridRoot, DataGridHeader, DataGridBody } from "@/components/data-grid/data-grid";
import { DataGridPaginationBar } from "@/components/data-grid-pagination/data-grid-pagination";

function OrdersGrid({ rows }: { rows: Order[] }) {
  const url = useDataGridUrlPagination();

  return (
    <DataGridProvider data={rows} columns={columns} getRowId={(row) => row.id} {...url}>
      <DataGridRoot>
        <DataGridHeader />
        <DataGridBody />
      </DataGridRoot>
      <DataGridPaginationBar pageSizeOptions={url.pageSizeOptions} />
    </DataGridProvider>
  );
}
```

A client grid goes back to page 1 itself when a filter changes. For a server grid, `useDataGridServerRows` resets the page, or call `url.onPageChange(1)` in your filter handler.

`page` (1-based) is omitted from the URL at page 1, and `pageSize` is omitted when it equals the
configured default. The full option list is on
[URL state](/docs/addons/url-state#pagination).
