A server grid sends its spec (`sorts`, `filters`, `searchText`) and a row range (`start`, `end`) to your route. The [query layer](/docs/data-modes/query-layer) checks the request and sends it over PostgREST through your Supabase client. Each filter tree goes into one `or=(...)`, with every value quoted and escaped. This route serves an `items` table with an `id`, a `name`, and a `qty`.

## The route [#the-route]

Create the client with the caller's token, so row-level security checks the user. `rpc` names the grid function of the table:

```ts title="lib/items-query.ts" fragment="needs @supabase/supabase-js"
import { createClient } from "@supabase/supabase-js";
import { defineColumnMap } from "@/components/data-grid-server-query/data-grid-server-query";
import { createSupabaseGridQuery } from "@/components/data-grid-server-query-supabase/data-grid-server-query-supabase";

const columns = defineColumnMap({
  id: { type: "number", numeric: "int8", primaryKey: true },
  name: { type: "text", searchable: true, maxLength: 200 },
  qty: { type: "number", numeric: "int4", aggregate: "sum" },
});

export function itemsQuery(auth: string) {
  const client = createClient(
    process.env.SUPABASE_URL!,
    process.env.SUPABASE_ANON_KEY!,
    { global: { headers: { Authorization: auth } } },
  );
  return createSupabaseGridQuery({
    client, table: "items", columns, rpc: "items_grid",
  });
}
```

```ts title="app/api/grid/route.ts"
import { handleGridRequest } from "@/components/data-grid-server-query/data-grid-server-query";
import { itemsQuery } from "./items-query";

export const POST = (req: Request) => {
  const auth = req.headers.get("Authorization");
  if (!auth) return new Response(null, { status: 401 });
  return handleGridRequest(req, itemsQuery(auth).fetchRows);
};
```

The client is the one in the [Drizzle example](/docs/server-data-examples/orm-examples/drizzle-example#the-client). Add the header `Authorization: Bearer <token>` to its `fetch`, with the access token of the signed-in user.

## The grid function [#grid-function]

Set values, aggregates, groups, pivots, long URLs, and large reads run in the grid function. Run `grid-query.sql` once per database. After each update of the add-on, run it again. The file replaces the `gridcn` functions, and your wrappers keep their calls. Then create one wrapper per table. List the fields of the mapped columns in its allow-list:

```sql title="supabase/migrations/items_grid.sql"
create or replace function public.items_grid(plan jsonb)
returns jsonb
language sql stable security invoker
as $$
  select gridcn.grid_query(
    'public.items'::pg_catalog.regclass,
    array['id', 'name', 'qty']::pg_catalog.text[],
    plan
  )
$$;
revoke execute on function public.items_grid(jsonb) from public, anon;
grant execute on function public.items_grid(jsonb) to authenticated;
```

Without `rpc`, these requests answer `unsupported`, and a long URL answers `limit-exceeded`.

A pivot takes 1 to 4 `groupBy` levels. The grid function answers the pivot keys in one call and the cells of the page's groups in a second call. Each group row at each level holds the cells of its own rows. A `time` pivot column answers `unsupported`. On a local PostgreSQL 17 over PostgREST, a page of 200 groups with 200 pivot keys over 100,000 rows takes about 75 ms. Without the pivot, the same page takes about 55 ms.

<Callout type="warn" title="Row-level security is the only tenancy boundary">
  Never make the wrapper or the `gridcn` functions SECURITY DEFINER. Row-level security then checks the owner, and the caller writes the plan. The function does not enforce `rowScope`. A direct caller reads every column of the allow-list, `serverOnly` columns included. Hide a column with a column GRANT. Never use the service role key in the route, because it bypasses row-level security.
</Callout>

## Limits [#limits]

- `maxRows` (default 1,000) is the `max-rows` setting of PostgREST, which cuts an answer without an error. A read of more rows goes to `rpc`. Without `rpc`, creation throws for a `limits.maxPageSize` plus 1 over `maxRows`. Then set `rpc`, or set `limits.maxPageSize` to `maxRows` minus 1 or less.
- `maxUrlLength` (default 8,000) bounds the request URL. A longer request goes to `rpc`.
- A literal `*` in a LIKE filter or the quick search answers `unsupported-value`, because PostgREST reads it as a wildcard.
- LIKE filters on a native enum or uuid column answer `unsupported`.
- `max_pivot_columns` (default 200) bounds the pivot cells per group. A wrapper can pass a lower value by name to `gridcn.grid_query`. The grid function then cuts the pivot keys, and `pivotOmitted` counts the cut columns. Keep it at or above the number of values of one request.
- The grid function groups a `timestamp` or `timestamptz` column by its millisecond. A group drills to every row of its millisecond, such as the rows that `now()` filled.

## Cursors, selection, and saves [#more-routes]

- [Page queries by cursor](/docs/scroll-mode/page-queries-cursor): `maxCursorBytes` (default 2,048) bounds the cursor, and every sortable text column needs `maxLength`.
- [Query the selected rows](/docs/rows-live-data/query-selected-rows): an id list goes into the URL while it fits, else to `rpc`. Without `rpc`, a long list answers `limit-exceeded`.
- [Validate server saves](/docs/save-server/validate-server-saves): each `where` is one PostgREST logic tree of the row id and `rowScope`.

A `where` is safe only as the sole argument of one `.or()`, as in `.update(values).or(where).select("id")`. In one `.or()` with another condition, the scope becomes one branch of the OR and stops narrowing.

`query.save(apply)` validates the change and hands its writes to your `apply`. A save is atomic only as far as `apply` is. Each REST call is its own transaction, so a loop of `.update()` calls is not atomic. Write the whole change in one database function of your own, which runs in one transaction. Call that function from `apply` with `client.rpc`.
