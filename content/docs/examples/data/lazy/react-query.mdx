Each scrolled block becomes a `fetchQuery`: TanStack Query dedupes concurrent blocks,
keeps every fetched block in the cache (`staleTime: Infinity`), and the hook's abort signal
still cancels the network call when a spec change replaces the request. Scrolling back never refetches.
The "windows in the query cache" counter in the demo bar makes that visible.

## The seam

```tsx
const queryClient = useQueryClient();

const server = useDataGridServerRows<Row>({
  mode: "scroll",
  getRowId: (row) => row.id,
  fetchRows: async ({ start, end, signal }) => ({
    rows: await queryClient.fetchQuery({
      queryKey: ["rows", start, end],
      staleTime: Infinity,
      queryFn: () => api.fetchRows({ start, end, signal }),
    }),
    totalRowCount: 10_000,
  }),
});
```

The flow in words: viewport → block (`[start, end)`) → query key → sparse rows. The query
key **is** the block, so two overlapping scrolls to the same block share one fetch, and
the cache entry survives for the session. `staleTime: Infinity` is what keeps a revisited
block from refetching, because the default (`0`) marks data stale immediately.

<Callout type="info" title="Why not useInfiniteQuery">
`useInfiniteQuery` fetches pages sequentially from page 0. A virtualized grid asks for
arbitrary blocks. Row 9,000 before row 50 exists. So the imperative `fetchQuery` is the
fitting seam: same cache, same dedupe, no page-ordering constraint.
</Callout>
