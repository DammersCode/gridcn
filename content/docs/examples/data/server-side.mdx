Everything in one place: header-click sort, the filter menu, quick search, and server
pagination all land in a single request. The view state is the query key, so revisiting a
state is instant from the cache, and `keepPreviousData` keeps the previous page on screen
while the next one loads. Nothing is filtered or sorted client-side. The fake server
applies every operator.

## The contract

The grid's store lives inside the provider, but the provider's `data` prop sits outside it.
So a small bridge component does both jobs: it reads the store (it has to be inside the
provider) and reports the fetched page up (the provider needs it).

```tsx
function RemoteStateBridge({ server, page, pageSize, onLoaded }) {
  const sortState = useDataGridSortState();
  const filterState = useDataGridFilterState();
  const searchText = useDataGridSearchText();

  const query = useQuery({
    queryKey: ["rows", page, pageSize, sortState, filterState, searchText],
    queryFn: () =>
      server.fetchPage({
        page,
        pageSize,
        sorts: sortState,
        filters: filterState,
        search: searchText,
      }),
    placeholderData: keepPreviousData,
  });

  useEffect(() => {
    if (query.data) onLoaded(query.data);
  }, [query.data, onLoaded]);

  return null;
}
```

Notes:

- `filters` <NewBadge /> is the filter tree: rows and groups, with no separate join. The top level combines with
  "and", and a group carries its own `join`.
- The request body is untrusted. Before you build a query, check that the tree is at most 2 groups
  deep, holds at most 64 rows, names only allowed columns, and uses `"and"` or `"or"` as every `join`.
  The [ORM recipes](/docs/examples/data/orm) show the check.
- The store hooks return **stable references** while the state is unchanged
  (`useShallow`), so the key only changes when a user actually sorts, filters, or searches
  (no render-time refetch loop).
- Pagination uses the **clamped** page from `pager.controls`: when a filter shrinks the
  result set, the bridge fetches the clamped page, never one past the end.
- Edits write through and invalidate, same as the pagination pages:

  ```tsx
  const onDataChange = (_next: readonly Row[], change: DataChange<Row>) => {
    api.save(change.ops);
    void queryClient.invalidateQueries({ queryKey: ["rows"] });
  };
  ```

## SWR variant

Same contract, different cache. The delta is the key/queryFn pair. The key becomes the
whole serialized view state, and the fetcher reads it positionally:

With SWR the previous-page-while-loading behavior has to be kept by hand (last data in a
ref, or the local-state pattern from the [pagination SWR page](/docs/examples/data/pagination/swr)).

## Shareable state

Wrap the same fetch in [DataGridUrlState](/docs/addons/url-state) and the view state (sort,
filters, search, page, page size) moves to the URL: reload or share the link and the grid
rebuilds the exact same request. The bridge's query key then reads the URL-synced state
instead of the store, and the URL becomes the request itself.
