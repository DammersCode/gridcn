`useDataGridServerRows` owns the sort, filter, search, page, and page size of a server grid. You write the one `fetchRows` function that calls your API. The hook fetches a page for each state, aborts a request that a newer state replaces, goes back to page 1 when the spec or the page size changes, and keeps the last good rows on screen while the next page loads or after an error. Nothing is filtered or sorted client-side.

## The wiring

```tsx
const server = useDataGridServerRows<Order>({
  getRowId: (row) => row.id,
  fetchRows: async ({ spec, page, pageSize, signal }) => {
    const answer = await api.orders({ ...spec, page, pageSize, signal });
    return { rows: answer.rows, totalRowCount: answer.total };
  },
});

<DataGrid {...server.gridProps} columns={columns} headerClickBehavior="sort" onSave={(change) => api.save(change.ops)} />
<DataGridPaginationBar {...server.pager} />
```

- The request holds `spec` (`sorts`, `filters`, `searchText`), `page`, `pageSize`, `start`, `end`, `cursor`, and `signal`. `start` is `(page - 1) * pageSize`, `end` is `start + pageSize`, and `cursor` is `undefined` in pages mode.
- `fetchRows` resolves `{ rows, totalRowCount }`. A server that sends no count resolves `{ rows, hasMore }`, and the footer shows "Page N" with Next and no Last. An omitted `totalRowCount` keeps the last known count; `null` declares it unknown.
- The hook checks every answer. `rows` must be an array, else the request fails. A `totalRowCount` that is not a non-negative integer reads as unknown, and one above 10,000,000 clamps to it. At most `pageSize` rows are kept. Each case warns once in development.
- `server.gridProps` carries `data`, `getRowId`, `sortMode="server"`, `filterMode="server"`, the controlled sort, filter, and search pairs, `totalRowCount`, `keepCheckedRows`, `loading`, `error`, and `onRetry`. Pass `headerClickBehavior="sort"` to sort on a header click. Put your own `onDataChange` and `getRowId` in the hook options: a spread override drops the hook's merge.
- A composed layout (toolbar, custom root) spreads `server.providerProps` onto `DataGridProvider` and `server.rootProps` (`loading`, `error`, `onRetry`) onto `DataGridRoot`. The demo does this.

## Errors and retry

A failed request sets `server.error` and keeps the last good rows visible. `DataGridRoot` shows the error state: a centered message with a Retry button over zero rows, and a slim alert bar under the header with rows present. Replace it with `errorState`, a node or a function receiving `{ error, retry }`. The text is `labels.grid.errorState`; the error itself is never rendered.

`server.retry()` repeats the request that failed and does nothing without an error. `server.refresh()` fetches the current page again and keeps the rows on screen until the answer lands, for example after a save. A row with a pending save or an open edit keeps its value. That guard mounts through `gridProps.plugins`, so a `plugins` prop of your own must start with `...server.gridProps.plugins`. The error clears when any new request starts. `server.status` is `"loading"`, `"error"`, or `"ready"` (`"error"` wins over `"loading"`), and `server.loading` is true while a request is in flight. `retry`, `refresh`, and every callback in `gridProps` keep their identity across renders.

`onError(error)` fires when a request fails. `onLoaded({ start, end })` fires when rows land. A throw in either is logged and does not drop the answer.

## Control the spec and the page

<NewBadge />

Pass `spec` with `onSpecChange`, `page` with `onPageChange`, and `pageSize` with `onPageSizeChange` to own the state yourself. Each pair works like a controlled input. `defaultSpec`, `defaultPage`, and `defaultPageSize` seed the state when you do not control it. A spec change asks `onPageChange` for page 1, except before the first answer lands, so a restored spec keeps a deep-linked page.

The `useDataGridUrlPagination()` result spreads straight in. With `<DataGridUrlState />` inside the provider, the URL restores the spec and the page and the hook sends one request:

```tsx
const url = useDataGridUrlPagination();
const server = useDataGridServerRows<Order>({ getRowId: (row) => row.id, fetchRows, ...url });
```

## Wait for typing to pause

<NewBadge />

The hook sends one request for each state and aborts a replaced one. To also wait for typing to pause, wait inside `fetchRows`. The wait ends early when the signal aborts:

```tsx
const delay = (ms: number, signal: AbortSignal) =>
  new Promise<void>((resolve, reject) => {
    const timer = setTimeout(resolve, ms);
    signal.addEventListener("abort", () => (clearTimeout(timer), reject(signal.reason)), { once: true });
  });

fetchRows: async ({ spec, page, pageSize, signal }) => {
  await delay(300, signal);
  return api.orders({ ...spec, page, pageSize, signal });
},
```

## Notes

- `filters` is the filter tree: rows and groups, with no separate join. The top level combines with "and", and a group carries its own `join`.
- The request is untrusted. Before you build a query, check that the tree is at most 2 groups deep, holds at most 16 groups and 64 rows, names only allowed columns, and uses `"and"` or `"or"` as every `join`. Cap the request body size too. The [ORM recipes](/docs/examples/data/orm) show the check.
- Keep a query cache in front of the API by calling it inside `fetchRows`, for example `queryClient.fetchQuery({ queryKey: ["rows", spec, page, pageSize], queryFn: () => api.orders(...) })`.
- To make the state shareable, wrap the grid in [DataGridUrlState](/docs/addons/url-state): the view state moves to the URL.
- Checks that survive pages and "select all matching" need `totalRowCount` and `keepCheckedRows`, which `gridProps` already carries. See [Selection over a server result](/docs/selection-keyboard#selection-over-a-server-result).
