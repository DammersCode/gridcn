When a server refuses some rows of a change, return those rows from `onSave`. The grid marks the rows `saving` while the promise is pending. It reverts only the refused rows and keeps everything the server accepted.

## Acknowledge each change [#acknowledge-each-change]

Send one request per operation, then return a rejection for each request that failed:

```tsx
import {
  DataGrid,
  type DataChange,
  type SaveAck,
  type SaveRejection,
} from "@/components/data-grid/data-grid";
import { columns, type Order } from "./orders";
import { sendOp } from "./api";

async function onSave(change: DataChange<Order>): Promise<SaveAck<Order>> {
  const results = await Promise.allSettled(change.ops.map(sendOp));
  const rejected = results.flatMap((result, i): SaveRejection<Order>[] =>
    result.status === "rejected"
      ? [{ rowId: change.ops[i]!.rowId, message: String(result.reason) }]
      : [],
  );
  return { rejected };
}

export function OrdersGrid({ rows }: { rows: Order[] }) {
  return (
    <DataGrid
      defaultData={rows}
      columns={columns}
      getRowId={(row) => row.id}
      onSave={onSave}
      onSaveRejected={({ rejected }) => alert(rejected[0]?.message)}
    />
  );
}
```

`sendOp` sends one request per operation, so each refusal maps to one row. If the change holds `move` operations, send them together as in [Translate operations into API calls](/docs/save-server/save-revert#translate-operations-into-api-calls). When that request fails, refuse every moved row.

With controlled `data`, `onDataChange` keeps your state in step and returns nothing. `onSave` is the only callback that answers the grid.

## What the answer means

- A promise that resolves with nothing accepts the whole change.
- A promise that rejects, or a handler that throws, refuses the whole change. Every row of the change reverts.
- `{ rejected: [] }` accepts the whole change.
- The grid reads at most 10,000 entries of `rejected`. It skips an entry without a string `rowId`. An answer whose `rejected` is not an array accepts the whole change.

{/* props: SaveRejection */}

| Field | Meaning | Default |
| --- | --- | --- |
| `rowId` | The row the server refused. | none |
| `columnId` | Refuses one cell of an update. | whole row |
| `message` | Text for `onSaveRejected`. The grid does not render it. | none |
| `current` | The row with the values the server holds. | none |

A cell reverts only while it still holds the refused value. A newer edit of the same cell stays.

## Put the server row in place [#current]

If you pass `current`, the revert writes that row in place of the old local row. A refused delete restores `current` without the resolver. A refused insert removes the row and ignores `current`. A refused move reverts its position. Pass a rejection with `current` like this:

```ts
import type { SaveRejection } from "@/components/data-grid/data-grid";
import type { Order } from "./orders";

const rejection = {
  rowId: "o-17",
  message: "Locked by another user",
  current: { id: "o-17", status: "shipped" } as Order,
} satisfies SaveRejection<Order>;
```

If a newer write to the row is pending or has settled, the grid ignores `current`. If `getRowId(current)` throws or differs from `rowId`, the grid ignores `current` and warns once in development.

## Detect a conflict on the server [#detect-a-conflict]

<NewBadge />

An `update` operation carries `prev`, the row before the edit, and its edited `cells`. When a stored field of an edited cell differs from `prev`, another user changed it: refuse the row with `current`. This handler assumes that each column id names a row field:

```ts
import type {
  DataOp,
  SaveRejection,
} from "@/components/data-grid/data-grid";
import type { Order } from "./orders";
import { db } from "./db";

export async function POST(request: Request) {
  const ops = (await request.json()) as DataOp<Order>[];
  const rejected: SaveRejection<Order>[] = [];
  for (const op of ops) {
    if (op.type !== "update") continue;
    const stored = await db.orders.find(op.rowId);
    const before = op.prev as Record<string, unknown>;
    const fields =
      op.cells?.map((cell) => cell.columnId) ?? Object.keys(before);
    if (!stored || fields.some((field) => stored[field] !== before[field])) {
      rejected.push({ rowId: op.rowId, current: stored ?? undefined });
    } else {
      await db.orders.update(op.rowId, op.row);
    }
  }
  return Response.json({ rejected });
}
```

Validate the body first, and run the check and the write in one transaction. On the client, `onSave` returns the parsed answer.

## Resolve a conflict [#resolve-a-conflict]

<NewBadge />

When a refusal carries `current`, the revert takes the server row. To decide per row, pass `resolveSaveConflict` to the provider. It receives `{ rowId, mine, theirs, change, message, signal }` for each refused row with a usable `current`, except on a `readOnly` grid. `mine` is the row in the grid, and `theirs` is `current`. Return one of these:

| Return | Result |
| --- | --- |
| `"theirs"` or nothing | The grid takes the server row. |
| `"mine"` | The grid keeps its row. |
| `{ row }` | The grid takes your merged row. |

<ComponentPreview name="data-grid-save-conflict-demo" />

`"mine"` and `{ row }` commit one change with `source: "merge"` on top of the server row. `onSave` receives it. History does not record it. A promise keeps the row `saving` until it settles. `signal` aborts when a newer write to the row starts or the grid unmounts.

This handler keeps the user's `note` and takes the server's other fields:

```tsx
import type { SaveConflictContext } from "@/components/data-grid/data-grid";
import type { Order } from "./orders";

function resolveSaveConflict({ mine, theirs }: SaveConflictContext<Order>) {
  return { row: { ...theirs, note: mine.note } };
}
```

A change that took server content has `DataChange.serverRowIds`. `useDataGridHistory` drops the older undo steps for those rows.

## React to a refusal [#react-to-a-refusal]

- The revert is one `onDataChange` call with `source: "rollback"`. The `reverts` field names the refused change. `onSave` never receives that call.
- `onSaveRejected({ change, rejected, error })` runs once per refused change, after the revert. If the promise resolved with `{ rejected }`, `error` is `null`. Otherwise `error` is the rejection reason.
- While the promise is pending, the row element carries `data-save-status="saving"`. After a refusal it carries `failed` until the next save of the row or `actions.clearSaveStatus()`.
- When the revert writes, `useDataGridHistory` removes the refused change from its undo stack. The whole entry goes, so the rows that the server accepted lose their undo step.
- On a `readOnly` grid, the grid skips the revert, warns once in development, and still calls `onSaveRejected`.
- If you replace the data before the answer, a refused update of a row that left the data reverts nothing. A refused delete puts the row back into the new data. When that matters, reload the rows in `onSaveRejected`.
- The callbacks run after the outermost write: `onDataChange`, then `onSave`, then plugin observers. After a refusal, the rollback `onDataChange` runs, then `onSaveRejected`. A throw in one callback does not stop the next.
