When a server refuses some rows of a change, return those rows from `onSave`. The grid reverts only the refused rows and keeps the rest.

## Acknowledge each change [#acknowledge-each-change]

Send one request per operation, then return a rejection for each request that failed:

```tsx
import {
  DataGrid,
  type DataChange,
  type SaveAck,
  type SaveRejection,
} from "@/components/data-grid/data-grid";
import { columns, type Order } from "./orders";
import { sendOp } from "./api";

async function onSave(change: DataChange<Order>): Promise<SaveAck<Order>> {
  const results = await Promise.allSettled(change.ops.map(sendOp));
  const rejected = results.flatMap((result, i): SaveRejection<Order>[] =>
    result.status === "rejected"
      ? [{ rowId: change.ops[i]!.rowId, message: String(result.reason) }]
      : [],
  );
  return { rejected };
}

export function OrdersGrid({ rows }: { rows: Order[] }) {
  return (
    <DataGrid
      defaultData={rows}
      columns={columns}
      onSave={onSave}
      onSaveRejected={({ rejected }) => alert(rejected[0]?.message)}
    />
  );
}
```

`sendOp` sends one request per operation, so each refusal maps to one row. To send `move` operations in one request, see [Translate operations into API calls](/docs/save-server/save-revert#translate-operations-into-api-calls). Refuse every moved row when that request fails.

## What the answer means

- A promise that resolves with nothing, or with `{ rejected: [] }`, accepts the whole change.
- A promise that rejects, or a handler that throws, refuses the whole change. Every row of the change reverts.
- An answer with more than 10,000 entries in `rejected` refuses every row of the change, as a thrown error does, and warns once in development.
- The grid skips an entry without a string `rowId`. A `rejected` that is not an array accepts the whole change.

{/* props: SaveRejection */}

| Field | Meaning | Default |
| --- | --- | --- |
| `rowId` | The row the server refused. | none |
| `columnId` | Refuses one cell of an update that lists `cells`. Any other operation is refused whole. | whole row |
| `message` | Text for `onSaveRejected`. The grid does not render it. | none |
| `current` | The row with the values the server holds. | none |

## Put the server row in place [#current]

If you pass `current`, the revert writes that row in place of the old local row. A refused delete restores `current` without `resolveSaveConflict`. See [Resolve a conflict](#resolve-a-conflict). A refused insert removes the row and ignores `current`. A refused move reverts its position.

The grid ignores `current` when a newer write to the row exists. It also ignores `current`, and warns once in development, when `getRowId(current)` throws or differs from `rowId`.

## Detect a conflict on the server [#detect-a-conflict]

An `update` operation carries `prev`, the row before the edit, and its edited `cells`. If a stored field of an edited cell differs from `prev`, another user changed it. Refuse the row with `current`. Otherwise write only the edited cells. This handler assumes that each column id names a row field:

```ts
import type {
  DataOp,
  SaveRejection,
} from "@/components/data-grid/data-grid";
import type { Order } from "./orders";
import { db } from "./db";

export async function POST(request: Request) {
  const body: unknown = await request.json();
  if (!Array.isArray(body)) {
    return Response.json({ error: "Expected a list" }, { status: 400 });
  }
  const rejected: SaveRejection<Order>[] = [];
  for (const op of body as DataOp<Order>[]) {
    if (op?.type !== "update" || typeof op.rowId !== "string") continue;
    const stored = await db.orders.find(op.rowId);
    const before = op.prev as Record<string, unknown>;
    const fields =
      op.cells?.map((cell) => cell.columnId) ?? Object.keys(before);
    if (!stored || fields.some((field) => stored[field] !== before[field])) {
      rejected.push({ rowId: op.rowId, current: stored ?? undefined });
    } else {
      const patch = op.cells
        ? Object.fromEntries(op.cells.map((c) => [c.columnId, c.value]))
        : op.row;
      await db.orders.update(op.rowId, patch);
    }
  }
  return Response.json({ rejected });
}
```

Run the check and the write of each row in one transaction. The client sends `change.ops` to this route and returns the answer to the grid:

```tsx fragment="the onSave of the grid"
onSave={async (change) => {
  const response = await fetch("/api/orders/changes", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(change.ops),
  });
  if (!response.ok) throw new Error(`Save failed: ${response.status}`);
  return response.json();
}}
```

## Resolve a conflict [#resolve-a-conflict]

When a refusal carries `current`, the revert takes the server row. To decide per row, pass `resolveSaveConflict` to the provider. It receives a `SaveConflictContext`, `{ rowId, mine, theirs, change, message, signal }` for each refused row with a usable `current`. It does not run on a `readOnly` grid. `mine` is the row in the grid, and `theirs` is `current`. Return one of these:

| Return | Result |
| --- | --- |
| `"theirs"` or nothing | The grid takes the server row. |
| `"mine"` | The grid keeps its row. |
| `{ row }` | The grid takes your merged row. |

`"mine"` and `{ row }` commit one change with `source: "merge"` on top of the server row. `onSave` receives it, and history does not record it. A returned promise keeps the row `saving` until it settles. `signal` aborts when a newer write to the row starts or the grid unmounts.

This handler keeps the user's `customer` and takes the server's other fields: `({ mine, theirs }) => ({ row: { ...theirs, customer: mine.customer } })`.

A change that took server content has `DataChange.serverRowIds`. `useDataGridHistory` drops older undo steps for those rows.

## React to a refusal [#react-to-a-refusal]

- The revert is one `onDataChange` call with `source: "rollback"`. The `reverts` field names the refused change. `onSave` never receives that call.
- `onSaveRejected({ change, rejected, error })` runs once per refused change, after the revert. If the promise resolved with `{ rejected }`, `error` is `null`. Otherwise `error` is the rejection reason.
- The row element carries `data-save-status="failed"` after a refusal. See [Save edits](/docs/save-server/save-edits#read-the-save-status).
- When the revert writes, `useDataGridHistory` removes the whole refused entry from its undo stack, also for rows the server accepted.
- A `readOnly` grid skips the revert, warns once in development, and still calls `onSaveRejected`.
- If you replace the data before the answer, a refused update of a row that left reverts nothing. A refused delete puts the row back.
- A throw in one callback does not stop the next.
