`updateCells` writes values into the grid by row id. Use it for live feeds that update many cells per second.

<ComponentPreview name="data-grid-streaming-demo" />

## Write patches [#usage]

Address each write by the `getRowId` value and the column id. Render the feed component inside `DataGridProvider`, next to `DataGridRoot`:

```tsx
import { useEffect } from "react";
import {
  useDataGridActions,
  type CellPatch,
} from "@/components/data-grid/data-grid";

type Quote = { symbol: string; price: number };

export function TickerFeed({ quotes }: { quotes: Quote[] }) {
  const actions = useDataGridActions();

  useEffect(() => {
    const id = setInterval(() => {
      const patches: CellPatch[] = quotes.map((q) => ({
        rowId: q.symbol,
        columnId: "price",
        value: q.price,
      }));
      actions.updateCells(patches);
    }, 250);
    return () => clearInterval(id);
  }, [actions, quotes]);

  return null;
}
```

One call is one batch. The grid applies all patches together and calls `onDataChange` once, with one `update` operation per touched row. Rows you do not patch keep their object identity and do not render again.

A hidden column takes patches like a visible one. The grid skips a patch for an unknown row or column, a read-only column, or an unchanged value. On a `readOnly` grid, every batch does nothing.

## Patch whole rows [#whole-rows]

`actions.updateRows([{ rowId: "AAPL", changes: { price: 214.5 } }])` takes `RowPatch` entries and patches several columns of one row at once. Each entry in `changes` becomes one patch. The options are the same as for `updateCells`.

## Sorted and filtered views [#sorted-and-filtered-views]

If a patch changes a value that the sort or filter reads, the row keeps its position and the grid sets a stale flag. Read the flag with `useDataGridViewStale` and give the user a control to re-sort. Render it inside the provider too:

```tsx
import {
  useDataGridActions,
  useDataGridViewStale,
} from "@/components/data-grid/data-grid";

export function ReSortBar() {
  const actions = useDataGridActions();
  const viewStale = useDataGridViewStale();
  if (!viewStale) return null;
  return <button onClick={() => actions.reconcileView()}>Re-sort</button>;
}
```

`reconcileView()` clears the flag. A change of sort or filter does the same. An edit, paste, fill, or cleared selection that touches such a column also marks the view stale.

The `reorder` option of `UpdateCellsOptions` takes an `UpdateCellsReorder` value and sets this behavior per call, for example `{ reorder: "immediate" }`:

| Value | Behavior |
| --- | --- |
| `"defer"` (default) | The value changes, the row holds its position, and `viewStale` becomes true. |
| `"immediate"` | The grid moves the patched rows to their new positions in the same call. |
| `"never"` | The value changes and `viewStale` stays false. |

If no patched column feeds the active sort or filter, `"defer"` acts as `"never"`.

`"immediate"` removes each patched row from the order, tests it against the filter again, and puts it back at its sorted position. The grid rebuilds the whole order when this batch and the earlier deferred batches touch more than 256 rows. After an edit, paste, fill, cell clear, undo, redo, rollback, row operation, or data swap, the next batch also rebuilds once.

With `sortMode="server"` and `filterMode="server"`, the grid does not read the sort or filter state, so the flag never turns on.

## Control the data yourself [#controlled-mode]

In controlled mode, store the array that `onDataChange` gives you in state, and pass it back as `data` unchanged. The grid recognizes its own array and keeps the sort, filter, and search results. Pass a stable `sortState` and `filterState`. A new array on each render counts as a change, and the grid computes the view again. If you rebuild the array before you store it, the grid computes those results again on every update.

## Undo and save [#undo-history]

A batch carries `source: "stream"`. The history add-on does not record that source, and `onSave` never receives it.

To make one batch undoable, pass `{ source: "edit" }` to `updateCells`. An `"edit"` batch reaches `onSave`. To record streams without that, list the sources for the history add-on. The list replaces the default, so keep the default sources in it:

```tsx fragment="inside your grid component"
const history = useDataGridHistory<Row>({
  recordSources: [
    "edit", "paste", "fill", "delete", "row-operation",
    "import", "replace", "app", "stream",
  ],
});
```

## What stays in place [#what-does-not-change]

A batch without `reorder: "immediate"` does not move the selection, the active cell, or an open editor. An immediate re-sort moves the open edit with its row.

If a value fails `validate`, the grid skips it and applies the rest of the batch. `onValidationError` then reports the skipped values with `source: "stream"`. See [Edit and validation events](/docs/events-state/edit-validation-events). When the producer already checked the values, set `skipValidation: true`.

A batch into a column with an async schema changes nothing until the schema answers. The accepted cells then commit together as one `onDataChange`. A write that changes the rows, or a rebuild of the view, supersedes the held batch, and the grid drops its late answer. This list covers the common triggers, not every path:

- A newer batch that also waits for an async schema, or an `"immediate"` batch that writes a value
- An edit, paste, fill, cell clear, undo, redo, rollback, or row operation
- A sort or filter change, a hidden or shown column, `reconcileView()` on a stale view, or a new `data`, `columns`, or `searchText` prop

A plain `updateCells` call that does not wait keeps the held batch, until the rows that wait for a re-sort pass 256. If every cell fails, the batch commits nothing. See [Validation](/docs/editing-cells/validation#on-bulk-paths).

## Read the verdict [#what-the-verdict-tells-you]

`updateCells` and `updateRows` return an `UpdateCellsVerdict`:

- `applied` counts the cells the call wrote.
- `skipped` holds one `UpdateCellsSkip` per patch that the grid checked and did not write, with its `patchIndex` and a `reason`. On a `readOnly` grid, `skipped` is empty. Two patches to one cell in one batch count once, and the last one wins.
- `pending` is `true` while an async schema holds the batch. `settled` resolves with the final verdict. A superseded batch resolves with `applied: 0` and no `skipped` entries.

| Reason | Meaning |
| --- | --- |
| `unknown-row` | The row id is not in `data`. |
| `unknown-column` | The column id is not a known column. |
| `hole` | The row is an unloaded scroll-mode row. |
| `readonly` | The column is read-only, has no write path (`accessorFn` without `setValue`), or the row is read-only through `readOnly(row)`. |
| `invalid` | The column's `validate` rejected the value. |
| `no-op` | The value equals the current value. |
