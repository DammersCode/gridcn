`updateCells` writes values into the grid by row id. Use it for live feeds that update many cells per second.

<ComponentPreview name="data-grid-streaming-demo" />

## Write patches [#usage]

Address each write by the `getRowId` value and the column id. Render the feed component inside `DataGridProvider`, next to `DataGridRoot`:

```tsx
import { useEffect } from "react";
import {
  useDataGridActions,
  type CellPatch,
} from "@/components/data-grid/data-grid";

type Quote = { symbol: string; price: number };

export function TickerFeed({ url }: { url: string }) {
  const actions = useDataGridActions();

  useEffect(() => {
    const socket = new WebSocket(url);
    socket.onmessage = (event: MessageEvent<string>) => {
      const quotes = JSON.parse(event.data) as Quote[];
      const patches: CellPatch[] = quotes.map((q) => ({
        rowId: q.symbol,
        columnId: "price",
        value: q.price,
      }));
      actions.updateCells(patches);
    };
    return () => socket.close();
  }, [actions, url]);

  return null;
}
```

One call is one batch. The grid applies all patches together and calls `onDataChange` once, with one `update` operation per touched row. Rows you do not patch keep their object identity and do not render again. The grid skips a patch for an unknown row id. To add a row, pass a new `data` array.

A call with `source: "stream"` <NewBadge /> (the default) takes at most 100,000 patches. The grid skips the patches after the limit. A stream `deleteRowsById` call takes at most 100,000 ids under the same rule.

A hidden column takes patches like a visible one.

A call with `source: "stream"` <NewBadge /> writes into a `readOnly` grid and into read-only columns and rows. A call with another `source`, for example `"edit"`, keeps every read-only check.

## Patch whole rows [#whole-rows]

`actions.updateRows([{ rowId: "AAPL", changes: { price: 214.5 } }])` takes `RowPatch` entries and patches several columns of one row at once. Each entry in `changes` becomes one patch. The options are the same as for `updateCells`.

## Sorted and filtered views [#sorted-and-filtered-views]

If a patch changes a value that the sort or filter reads, the row keeps its position and the grid sets a stale flag. Read the flag with `useDataGridViewStale` and give the user a control to re-sort. Render it inside the provider:

```tsx
import {
  useDataGridActions,
  useDataGridViewStale,
} from "@/components/data-grid/data-grid";

export function ReSortBar() {
  const actions = useDataGridActions();
  const viewStale = useDataGridViewStale();
  if (!viewStale) return null;
  return <button onClick={() => actions.reconcileView()}>Re-sort</button>;
}
```

`reconcileView()` clears the flag. A change of sort or filter does the same. An edit, paste, fill, or cell clear that touches such a column also marks the view stale.

The `reorder` option of `UpdateCellsOptions` takes an `UpdateCellsReorder` value and sets this behavior per call, for example `{ reorder: "immediate" }`:

| Value | Behavior |
| --- | --- |
| `"defer"` (default) | The value changes, the row holds its position, and `viewStale` becomes true. |
| `"immediate"` | The grid moves the patched rows to their new positions in the same call. |
| `"never"` | The value changes and `viewStale` stays false. |

If no patched column feeds the active sort or filter, `"defer"` acts as `"never"`.

`"immediate"` finds each patched row and keeps the order when every row still sits between its neighbors. Otherwise it removes the patched rows, tests them against the filter again, and puts them back at the positions a full sort gives them. A batch that cannot change a sort or filter value skips this work. The grid rebuilds the whole order when this batch and the earlier deferred batches touch more than 256 rows. After an edit, paste, fill, cell clear, undo, redo, rollback, row operation, or data swap, the next batch also rebuilds once.

With `sortMode="server"` <NewBadge /> or `filterMode="server"`, the server orders the rows. A push marks the row stale and the hook can refetch. See [Push into a server-ordered view](/docs/rows-live-data/push-server-ordered-view).

## Control the data yourself [#controlled-mode]

In controlled mode, store the array that `onDataChange` gives you in state, and pass it back as `data` unchanged. The grid recognizes its own array and keeps the sort, filter, and search results. Pass a stable `sortState` and `filterState`. A new array on each render counts as a change, and the grid computes the view again.

## Undo and save [#undo-history]

A batch <NewBadge /> carries `source: "stream"`. The history add-on does not record it, and `onSave` never receives it. Undo writes only the cells of its edit, so values pushed into other cells stay. A push into a row with a save in flight is skipped with reason `saving`. Push it again after the save settles.

To make one batch undoable, pass `{ source: "edit" }` to `updateCells`. An `"edit"` batch reaches `onSave`. To record streams without that, list the sources for the history add-on. The list replaces the default, so keep the default sources in it:

```tsx fragment="inside your grid component"
const history = useDataGridHistory<Row>({
  recordSources: [
    "edit", "paste", "fill", "delete", "row-operation",
    "import", "replace", "app", "stream",
  ],
});
```

## What stays in place [#what-does-not-change]

A batch without `reorder: "immediate"` does not move the selection, the active cell, or an open editor. An immediate re-sort moves the open edit with its row.

If a value fails `validate`, the grid skips it and applies the rest of the batch. `onValidationError` then reports the skipped values with `source: "stream"`. See [Edit and validation events](/docs/events-state/edit-validation-events). When the producer already checked the values, set `skipValidation: true`.

A batch into a column with an async schema changes nothing until the schema answers. The accepted cells then commit together as one `onDataChange`. A write that changes the rows, or a rebuild of the view, supersedes the held batch, and the grid drops its late answer. The common triggers are:

- A newer batch that also waits for an async schema, or an `"immediate"` batch that writes a value
- An edit, paste, fill, cell clear, undo, redo, rollback, or row operation
- A sort or filter change, a hidden or shown column, `reconcileView()` on a stale view, or a new `data`, `columns`, or `searchText` prop

A plain `updateCells` call that does not wait keeps the held batch, until the rows that wait for a re-sort pass 256. If every cell fails, the batch commits nothing. See [Validation](/docs/editing-cells/validate-rows-cross-field#on-bulk-paths).

## Read the verdict [#what-the-verdict-tells-you]

`updateCells` and `updateRows` return an `UpdateCellsVerdict` with `applied`, `skipped`, `pending`, and `settled`. [Read a push verdict](/docs/rows-live-data/read-push-verdict) lists the skip reasons. It also shows how to [flash the written cells](/docs/rows-live-data/read-push-verdict#flash-cells).
