Loaded rows stay in the sparse `data` array. A long scroll through a large result grows the array. The hook unloads rows itself above `maxLoadedRows`, as the next section says. A spec change, a changed row count, a remount, or `evict` also removes them. `refresh()` drops the loaded rows outside the rendered rows. So does a row operation on a result with a row count. Four levers tune the array: `maxLoadedRows`, `refresh`, `evict`, and `getLoadedRanges`.

## Cap the loaded rows [#max-loaded-rows]

<NewBadge />

Scroll mode keeps at most `maxLoadedRows` rows loaded on a random access source (default 10,000). When more are loaded, the hook unloads the blocks that the user viewed longest ago outside the rendered rows plus `overscan` plus one block. Rows with an open edit, a pending save, or an unsaved change, and the row under the active cell, stay in `data`. They stop counting as loaded, so the next window fetches their block whole. Pass `maxLoadedRows: Infinity` to keep every row.

## Memory and retention [#memory--retention]

1. Pick the row ranges to drop. `server.getLoadedRanges()` lists the loaded ones, merged and sorted. It never triggers a render, so call it in an effect or a handler.
2. Call `server.evict(rowRange)` for each row range you want to drop. A row range is a `RowRange`, `{ start, end }` with an exclusive `end`. A partial overlap drops the intersection only, and the rest stays loaded.
When the user scrolls back into an evicted row range, the hook fetches the rows again.

`server.unloadedCount` counts the rows that render as skeleton rows. A sequential source reports its one block of skeleton rows.

An eviction policy is your decision. This grid drops the loaded blocks that are at least 500 rows away from the rendered rows. It rounds the edges to multiples of `blockSize`, so a block that comes back asks for the same rows as before:

```tsx
"use client";

import { DataGrid, defineColumns } from "@/components/data-grid/data-grid";
import {
  useDataGridServerRows,
} from "@/components/data-grid-server/data-grid-server";

type Order = { id: string; customer: string };

const columns = defineColumns<Order>()([
  { id: "customer", header: "Customer", accessorKey: "customer" },
]);

const BLOCK_SIZE = 50;
const MIN_DISTANCE = 500;

export function OrdersGrid() {
  const server = useDataGridServerRows<Order>({
    mode: "scroll",
    blockSize: BLOCK_SIZE,
    fetchRows: async ({ start, end, signal }) => {
      const query = `offset=${start}&limit=${end - start}`;
      const response = await fetch(`/api/orders?${query}`, { signal });
      const answer = await response.json();
      return { rows: answer.rows, totalRowCount: answer.total };
    },
  });

  return (
    <DataGrid
      {...server.gridProps}
      columns={columns}
      className="h-96"
      onRenderedRowsChange={(range) => {
        server.gridProps.onRenderedRowsChange(range);
        const behind = range.start - MIN_DISTANCE;
        const ahead = range.end + MIN_DISTANCE;
        server.evict({
          start: 0,
          end: Math.floor(behind / BLOCK_SIZE) * BLOCK_SIZE,
        });
        server.evict({
          start: Math.ceil(ahead / BLOCK_SIZE) * BLOCK_SIZE,
          end: Number.MAX_SAFE_INTEGER,
        });
      }}
    />
  );
}
```

Call the hook's own `onRenderedRowsChange` first. A prop after the spread replaces it, and the hook needs the rendered row range to fetch blocks.

Two behaviors matter for a policy of your own:

- `evict` aborts the requests it covers, and a request that started before the evict drops its answer. It keeps rows with an open edit, a pending save, or an unsaved change, and the row under the active cell.
- An evicted row loses an edit that you did not persist, because the hook does not own persistence. When an edit targets a row that the hook evicted before the merge, the hook warns once in development. See [Load rows while scrolling](/docs/scroll-mode/load-rows-while-scrolling#editing-loaded-rows).

`evict` clamps the row range to `[0, totalRowCount)`. A sequential source ignores it.

## Refresh the rows in view

Call `server.refresh()` after the result behind the same spec changes, for example after a server-side import. It fetches the blocks around the rendered rows again and keeps them on screen until the answers land. It drops every other loaded block. A sequential source fetches again from the first block, up to the rendered rows.

A pending insert or delete is one whose `onSave` promise has not settled. A refresh keeps a row that has an open edit or a save in flight. The row keeps its local value. If the answer carries a row with a pending delete, the row stays gone.

If the answer lacks a pending insert and no answer row sits in its slot, the insert returns to that slot. If an answer row sits there, the insert stays hidden. A result with a row count refreshes again once no pending insert or delete remains. A refresh of a sequential source that ends before a pending insert can drop it until its save settles.

`gridProps.plugins` mounts the guard that applies these rules. A `plugins` prop of your own replaces the guard. Put the hook's plugins first, as in `plugins={[...server.gridProps.plugins, myPlugin]}`. When an edit happened and the guard never mounted, `refresh()` warns once in development.

Call `refresh()` <NewBadge /> after your `onSave` promise settles to pick up fields that the server computes. The hook can do it for you. See [Save edits](/docs/save-server/save-edits).

## Refresh on a timer [#revalidate]

<NewBadge />

Set `revalidateInterval` (milliseconds, at least 1000) to call `refresh()` on a timer while the page is visible. A tick waits for a request in flight, and every refresh restarts the clock. A sequential source skips a tick while the rendered rows end beyond 10 blocks. The default is off. Pages mode takes the same option.

When live pushes leave rows out of order for the server's sort, set `reshapeDelay` to refetch after a push. See [Stream updates](/docs/rows-live-data/push-server-ordered-view).

Undo and redo compose with the `onDataChange` of the hook. See [Run history with scroll mode](/docs/save-server/undo-server-data#with-scroll-mode).

## Limits with server state [#modes]

<NewBadge />

The limits, the timer, and `evict` follow the spec of the hook in every setup:

- **Server sort and filter.** The hook sets `sortMode="server"` and `filterMode="server"`. A sort or filter change starts the blocks over, so no limit holds rows of the old order.
- **Controlled state.** Pass `spec` with `onSpecChange`, or feed the hook from `sortState`, `filterState`, and `searchText` that your app owns. A changed spec drops the loaded rows and aborts the requests in flight.
- **Your own `onDataChange`.** The `onDataChange` option of the hook runs after the merge. Rows that your handler keeps outside the hook are not covered by `maxLoadedRows`.
