# Changelog 2.0

Changes of release 2.0 that are not breaking. The breaking changes are in [CHANGELOG.md](CHANGELOG.md). The format loosely follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## Core

- Row ids that start with `__` belong to the grid, such as the ids of pinned and unloaded rows.
- `DataGridHeaderFilter`, `DataGridHeaderDropdown`, and `DataGridKeybindingsDialog` accept `className`. It merges into the filter button, the menu content, and the dialog content.
- A plugin whose `name` an earlier plugin already uses is ignored with all its members. Its `commands` and `keymap` still merged, and its command won a name conflict with the first plugin.
- A plugin `keymap` entry names a command that the plugin defines. A plugin that named a built-in action, such as `selectAll`, in `commands` and `keymap` lost the command but replaced the action's default keys. The development warning for such an entry says that the action is a built-in action.
- A plugin `keymap` entry is the full binding list of its action, like the `keymap` prop: the list replaces the default bindings, a key that the default keymap has stays when the entry lists it, and keys that differ only in letter case count once. An empty list unbinds the action. The grid no longer drops a restated default key, and the "repeats a key" development warning is gone. Before, a plugin that listed `mod+z` with a new key for `undo` lost `mod+z`.
- `onPageChange` and `onPageSizeChange` fire after the grid writes the change, like `onSortChange`; a controlled prop still gets the next value. A throw in one of them, in `onColumnLayoutChange`, `onColumnResizing`, `onValidationError`, or `onEditEnd`, no longer stops the write or the other callbacks of the change: the grid rethrows the first error after they ran. A throw in `onSelectionChange`, `onActiveCellChange`, or the `onEditEnd` of an edit that a view change ends goes to the console instead of skipping the grid's other updates.
- `useDataGridRowIdToViewRow` maps a duplicate row id to the first row that carries it, like the rest of the grid. It mapped the id to the last row, so presence highlights landed on the wrong duplicate.
- The sticky viewport track now follows the scroll position once it is more than 1,000,000 px away (was 4,000,000 px), which keeps the sticky offset small on tall grids. This hardens the grid against a Firefox-only header flicker on fast scrolls and big jumps that could not be reproduced, so the report stays open.
- The skeleton bars of loading cells and rows, the column menu trigger, and the header filter trigger take the theme radius (`rounded-md`). The height-limit warning in development links the Row limits page.
- `gateTimeoutMs` (one number, or a number for each gate name) aborts an async gate (`onBeforeDeleteRows`, `validateRow`, `onBeforeEditStart`, `createRow`, `duplicateRow`, `processPaste`) whose promise has not settled in time, and `onGateAborted({ gate, reason })` reports every gate the grid stopped waiting for (`"timeout"`, `"changed"`, `"superseded"`, `"cancelled"`, `"reset"`). Both are off by default; a gate still waits for its promise.
- The grid compares the `labels` prop by content, so a literal object of strings no longer needs `useMemo`. A label that is a function still counts as changed when its identity changes.
- Clicks and key presses re-lay out the rows canvas less: every body cell carries an integer `z-index`, and unpinned selection, active-cell, fill and presence overlays are absolutely positioned. A custom cell renderer's non-portalled `z-index` content stays inside its own cell. Rows no longer re-render on every click or key under `StrictMode`, and the grid root no longer re-renders when the active cell moves inside the rendered column window.
- The provider prop `inputDebounceMs` (default 200, `0` commits each keystroke) sets the wait of the toolbar search, the filter value inputs, the set-filter search (was 150), the find & replace field (was 150), and the lookup editor. `DataGridSearch debounceMs` still overrides it for one box. The URL state add-on no longer waits 300 ms before it writes the search text; it writes the already debounced value and the adapter coalesces the writes. The search, the filter value inputs, and the find & replace field now commit text that is still waiting on blur, on Enter, and when the popover or search box unmounts (it was dropped), ignore Enter and wait during an IME composition, keep the typed text when an older commit echoes back late, and the `isBetween` inputs keep both values after two quick edits. Escape in find & replace drops the waiting text. The set-filter search only waits `inputDebounceMs`. New hook `useDebouncedInput` and `useDebounce`; see the next entry.
- The development warnings about `data` with `defaultData`, `selection` with `defaultSelection`, and a store with sync props fire once for each grid, not once for each page load.
- Async gates take an `AbortSignal`. The gates are `processPaste`, `validateRow`, `onBeforeEditStart`, `createRow`, `duplicateRow`, `onBeforeDeleteRows`, the `mapColumn` default of the import dialog, and its `createRow`. The signal is the last argument: `processPaste({ cells, target, signal })`, `validateRow(row, rowId, { signal })`, `onBeforeEditStart(cell, { signal })`, `createRow(index, { signal })`, `duplicateRow(row, index, { signal })`, `onBeforeDeleteRows({ rowIds, hiddenCount, signal })`, and `mapColumn(header, index, { signal })`. The signal aborts when a newer run of the same gate replaces the run, when the result can no longer apply (read-only, the row is gone, the cursor moved, the data changed), and when the grid unmounts. The grid drops an aborted result and does not warn about a rejection after an abort. A callback that ignores the new argument keeps working.
- `useDataGridGatePending()` returns the set of gate names whose promise has not settled. The grid root carries `data-gate-pending` (the gate names, separated by spaces) while the set is not empty. Docs: the "Cancel async gates" page covers the signal and the pending state.
- `processPaste`, `processCellFromClipboard`, `validateRow`, `onBeforeEditStart`, `createRow`, and `duplicateRow` accept a promise, and so do the `mapColumn` default and the `createRow` prop of the import add-on. A synchronous result takes the same path as before. A pending promise blocks a second request of the same gate. A rejection cancels with no write. The grid reads its state again when the promise settles and drops a late result for a `readOnly` grid or a row that is gone. `validateRow` does not hold the write: its verdict merges into the cell errors when it settles. Docs: an async gates demo on the validation examples.
- A client-only mount renders no data rows in its first commit, and measures the scroll element and the page direction in the layout effect that attaches it. The server render and the hydration keep their 30-row preview. On the mount benchmark (`research/perf-mount.md`: 1,000 rows, 8 columns, 500 px tall, headless Chromium 153 on an i7-13850HX), the first painted rows arrive after 42 ms instead of 72 ms on a cold mount and after 25 ms instead of 51 ms on a warm one. A right-to-left page and a flex column layout no longer paint one frame with the wrong direction or width. `autosizeOnMount` runs once the rows are mounted.
- Presence: `setPresenceHighlights` validates every peer entry. It clears every highlight for a payload that is not an array, keeps only known fields, drops entries with a missing, non-string, or oversized `id`, and keeps at most 1000 entries. A non-string `label` is removed and a label over 64 characters is truncated. A non-string `color` paints as `var(--color-primary)`. Before, an object `label` crashed the overlay.
- `DataGrid` and `DataGridRoot` take `markerWidth`, the marker track width in px. It overrides the width of the `rowMarkers` mode, so a six-digit row number or wide `renderMarker` content gets room: `<DataGrid rowMarkers="number" markerWidth={72} />`.
- The `fetchOptions` request of the lookup cell carries the edited `row`, its `rowId`, and the `columnId`, so a dependent lookup (a city list for the country of the row) reads the row without a ref fed from `onBeforeEditStart`. Pasted labels still resolve through the label cache, which has no row.
- `updateCells` and `updateRows` take `{ flash: true }` to flash the cells they applied: at once for a synchronous batch, after `settled` for a held one. Cells of hidden columns do not flash. `actions.flashCells` stays for arbitrary cells. The default is no flash.
- `renderCell` receives `options` (the column `options`) like a cell type's `Cell`. Before, `options` was `undefined` and the column `options` had to be read from `column.options`.
- An inline `getRowId` function no longer makes the grid write a new store state on every render. The grid keeps the old function when the new one returns the same ids for the same `data` array. The docs examples drop the default `getRowId={(row) => row.id}`.
- `DataGrid` takes `renderHeaderCell`. The `data-grid` barrel exports `isFilterGroup` and the types `StandardSchemaV1` and `HeaderFilterRenderer`.
- `getRowClassName` and `getCellClassName` need no stable identity, and the development warning about their identity is gone. Equal inline group header nodes keep the group model.
- The scroll shadows use utility classes, so a plain `background-image` rule restyles them without `!important`.
- `applyChange` defaults `getRowId` to the row `id`.
- Every console message and thrown error of the registry starts with `[data-grid]` (an add-on: `[data-grid-<add-on>]`). Some started with `gridcn:`.
- `createDataGridHooks<TData>()` returns the row-reading hooks typed for one row type: `export const { useDataGridRow, useDataGridApi } = createDataGridHooks<Order>();`. `columnLabelText` is on the `data-grid` barrel.
- `defaultSortState`, `defaultFilterState`, `defaultSearchText`, and `defaultColumnLayout` accept a function that runs once on the client after mount, so a seed can read `localStorage` or the URL.
- `onSelectionChange` details carry `phase`: `"drag"` for each step of a pointer drag, then `"end"` on release. Every other change reports `"end"`, so `phase === "end"` skips the steps.
- `renderMarker` receives `isChecked`. `isRowChannelSelected` still works and is deprecated.
- The header menu and the header context menu list Move toward start, Move toward end, Widen column, and Narrow column (labels `contextMenu.moveTowardStart`, `moveTowardEnd`, `widenColumn`, and `narrowColumn`). A move that would change nothing, such as at a column group edge, is disabled.
- `setColumnOrder` returns `{ ok: true }` or `{ ok: false, reason }`, and `canSetColumnOrder` returns the same without the move.
- The date editor loads the calendar (`react-day-picker`, `date-fns`) on its first open, so a grid ships no date picker until a user opens one.
- New development warnings: an async gate that stays pending for 30 seconds without `gateTimeoutMs`, partial `data` under a client sort or filter with `totalRowCount`, a `number` or `date` column with `locale` and no `format` or `displayFormat`, and `defaultData` that fills after an empty seed.

## Selection and editing

- A page change clears the active cell instead of leaving it on whichever record now sits at the same coordinates. Search and find and replace still select the match they jump to.
- `history.record` of `useDataGridHistory` and of `useDataGridState` returns `false` before the grid mounts and when every operation inserts a row that `data` already holds, and `true` otherwise. On a `readOnly` grid it writes nothing and returns `false`. The `refreshAfterSave` report adds `changes` (at most 100, oldest first) and `pending`.
- `history.record` is idempotent: an insert of a row that `data` already holds is skipped, with a development warning, so applying the change to your own array first no longer writes it twice.
- `onRowActionSkipped({ action, reason })` fires whenever `insertRows`, `duplicateRows`, or `deleteRows` does nothing, and when the Insert row, Duplicate row, or Delete rows shortcut hits one of `"readOnly"`, `"no-factory"`, `"hidden-rows-only"`, or `"all-matching"` (the last two come from shortcuts only; a shortcut calls the action otherwise; Insert row with no active cell reports nothing, and Duplicate row or Delete rows with no selection and no active cell report nothing when none of those reasons applies). A disabled row item of the context menu runs nothing and fires nothing; it shows the reason as a tooltip (`labels.contextMenu.rowActionReadOnly`, `rowActionHiddenChecked`, `rowActionAllMatching`).
- `insertRow`, `insertRows`, `duplicateRows`, `deleteRows`, and `deleteRowsAt` return `{ ok: true }` or `{ ok: false, reason }` instead of nothing, so a skipped action says why.
- `DataGridStatusBar` shows a select-all banner when `totalRowCount` is set and `checkedRowsLifetime` is `'across-filters'` (the default with `totalRowCount`). With every row of the page checked and a larger result it offers "Select all 237 matching" ("Select all matching" when the size is `null`); after that it reads "All 237 selected." with "Clear selection". `selectAllMatching()` announces the real count in the live region. New labels: `labels.grid.allMatchingChecked` ("All matching rows checked"), `labels.statusBar.pageSelected`, `selectAllMatching`, `allSelected`, `clearSelection`. The `data-grid-status-bar` item depends on `button`. The `data-grid-server-selection-demo` example uses the banner instead of its own button.
- `validateRow` also runs for the rows that `actions.commitChange` inserts or updates, for every change source except `"stream"`. Before, an import applied with `commitChange` skipped it, and the imported rows showed no cross-field errors; an undo or a rollback left the error of the undone edit in place. A verdict can be a promise, as for edits, and a newer change to the row cancels a pending verdict. If your `validateRow` is costly, it now runs once per imported row, and once per row that an undo, a redo, a rollback of a refused save, or a merge restores, so a refused bulk write makes one call per restored row. Async verdicts that settle together now merge into the cell errors with one write, so an async `validateRow` over a large import or paste no longer slows down with the row count.
- Selection over a server result. The provider prop `totalRowCount` (`number | null`, `null` for an unknown size) declares that `data` is a window of a larger result. With `checkedRowsLifetime="across-filters"`, a checked row that leaves `data` stays checked by row id in every mode (server and client pagination, lazy rows, `sortMode="server"`, `filterMode="server"`) and shows checked again when it returns. `actions.selectAllMatching()` checks the whole result, rows that load later show as checked, and an unchecked row is excluded by id. `useDataGridSelectedRows()` returns `{ mode: "ids", ids, excludedIds, count }` or `{ mode: "allMatching", ids, excludedIds, count, spec }` for a bulk action; `count` is `null` when the result size is unknown, and `spec` holds the sort, filters, and search text the grid held. While "all matching" is on, the Delete rows, Duplicate row, and Move rows shortcuts do nothing and `onBeforeDeleteRows` is not called; run the action through your own endpoint. The remembered set holds at most 100,000 ids. `useDataGridHiddenCheckedCount()` is `0` while "all matching" is on. A change of the filter or the search text, and `actions.deleteRows`, leave "all matching". Without `totalRowCount`, nothing changes. Docs: a "Select server rows" page with the live demo `data-grid-server-selection-demo`.
- A cell with an open editor and an error message carries the message as its `title`, so hovering it shows the message. A cell that is not being edited keeps the tooltip.
- The inline error line of an editing cell is visible. The cell clipped it, so a rejected value showed only the red ring. The line now escapes the cell, widens to its text (up to 16rem), flips above the cell at the bottom edge of the grid, and anchors to the cell's end side at the side edges. An editing cell no longer clips its content, so a custom `Editor` wider than its cell spills over the neighbors.
- The fill drag and the column resize drag end when the window loses focus; the fill drag ends without writing, and the resize keeps the width shown at that moment. The fill drag captures the scroll element, so it also survives auto-scroll past its source and ends on `lostpointercapture`.
- Duplicating several rows reports each copy's insert `index` as its final position, and `duplicateRow` and `getRowId` receive that index. Redo and `applyChange` now keep the copies in the order the grid showed. Before, the indexes counted the rows before the whole batch, so redo placed later copies one row early.
- `select` `options.choices` accepts plain strings. A string is a choice whose value and label are the same text, and strings mix with `{ value, label }` objects in one array: `choices: ["Open", "Done"]`.
- `DataGridActions` drops the internal members `armRowDragAnchor` and `setEditingError` and the `rejection` parameter of `commitCellEdit`. Add-on authors reach them as `_armRowDragAnchor`, `_setEditingError`, and `_commitCellEdit` through the internal actions of the SDK. `commitCellEdit(value, movement?)` is unchanged for documented code.
- `actions.editRows(updates)` runs `updateRows` with `source: "edit"` and `reorder: "immediate"`, so a bulk edit reaches undo and `onSave`.
- `deleteRowsAt` and `duplicateRowsAt` accept a plain number array.
- A cell type `validate` receives the column `options` as its third argument.
- In the `reorder` family of `rowMarkers` modes, the `renderMarker` ctx carries `reorderHandleProps`, so a custom marker can reorder rows.
- The type of `processCellFromClipboard` shows its promise form.
- `rejectText()` refuses text in a cell type's `fromText` or in a parse hook. The cell keeps its value and the grid reports the text, as the built-in types do.
- A function `validate` receives `ctx` as its third argument: `rows`, `batch` (every cell of the column that the same write sets), and `valueOf`. `unique()` rejects a value that another row holds, also inside one paste or fill.
- Rows that a user change wrote (edit, paste, fill, delete, cut, replace, import, row operation) carry `data-row-changed`. An undo, a push, or new `data` clears it.
- `setRowCheckedAt` takes a view row number, like `deleteRowsAt` and `duplicateRowsAt`. A `ViewIndex` still works.
- `updateCells`, `updateRows`, and `editRows` with a source other than `"stream"` on a `readOnly` grid list every patch in `skipped` with the reason `"readonly"`.
- `processCellFromClipboard` receives `ctx.signal` and counts as a gate: `useDataGridGatePending()` lists it while a promise is pending, and `gateTimeoutMs.processCellFromClipboard` aborts it. `gateTimeoutMs.mapColumn` aborts a pending import `mapColumn`, which falls back to the built-in column match.
- A paste, fill, or clear that an async column `validate` holds marks the gate `"validate"` pending, and `gateTimeoutMs.validate` aborts it. A paste aborts an earlier paste whose gate or async schema is still pending (`onGateAborted` reason `"superseded"`).
- The move-rows shortcuts report `"disabled"` to `onRowActionSkipped` without a reorder `rowMarkers` mode.

## Sorting, filtering, and search

- A paged grid searches every page: `searchMatches` and the match count cover the whole view, the highlights show the matches on the shown page, and next and previous match (toolbar search, find and replace) jump to the page of the match. Find and replace's "replace all" covers every page. `reorderRows` and `moveRowsBy` work inside a paged grid with page-relative rows: a move stays on the shown page, a move past the page edge does nothing, and the checked rows and the active cell follow their rows (a sort or filter still blocks them).
- The sort arrow shows in the string header of a sorted column that is not `sortable: false`, whatever `headerClickBehavior` says, so a sort restored from the URL is visible and no longer needs a docs workaround.
- Custom filter operators. List `{ id, label, input?, match? }` in the `filter.operators` of a column or a cell type: the operator select shows `label`, `input` (`single`, `range`, `list`, `none`) picks the value widget, and `match(text, filter)` evaluates it on the client. With `filterMode="server"` the spec carries the id and `match` is never called. The URL param round-trips a custom id through `useDataGridUrlState`.
- `ColumnDef.filter.compare(text, bound)` orders a column's cells for `gt`, `gte`, `lt`, `lte`, and `isBetween` instead of the numeric-then-text default.
- The find and replace panel shows "Searches loaded rows only" on a grid with a `totalRowCount` or a server `sortMode` or `filterMode`. New label: `findReplace.scopeLoadedRows`; an empty string hides the note.
- `useDataGridFindReplace({ processReplace })` (a gate, named like `processPaste`) runs after the panel builds the replace plan and before it writes. Return the plan to write, or `false` to cancel; a plan longer than `replaceAllLimit` cancels. A patch on a hidden column is skipped with the reason `"hidden"`, as in the built-in plan. New label: `findReplace.replaceCancelled`.
- Server-side filtering. The provider prop `filterMode: "client" | "server"` is the counterpart of `sortMode`. It defaults to `"server"` when `totalRowCount` is set and to `"client"` otherwise. With `"server"`, the grid tracks `filterState` (filter menu, header filters, `data-filtered`, `onFilterChange`) but never filters `data`, so the view keeps one row per index and the range of `onRenderedRowsChange` maps to data indices on a lazy grid. The filter is skipped in every view rebuild, row operation, and streaming write, and `checkedRowsLifetime="across-filters"` behaves like `"until-cleared"` without `totalRowCount`, like under `sortMode="server"`. A server filter change announces nothing when it changes; with `announceResults`, the end of the next load announces the result. The `onRenderedRowsChange` JSDoc now says the range is a view-row range.
- The provider prop `fetchFilterValues({ columnId, query, filters, signal })` supplies the set values of the header filter popover and of the `isAnyOf` input in the filter menu from a backend. A column with `options.choices` keeps its list. The grid keeps at most 1,000 labels per answer and remembers at most 1,000 labels across searches, aborts the request on a new search, a column switch, a closed popover, and unmount, and drops stale answers. New labels: `toolbar.headerFilterLoading` and `toolbar.headerFilterError`. New types: `FetchFilterValues`, `FetchFilterValuesContext`, `FilterValue`.
- **Faster client-side sorting.** A sort by a `number` column or a `text` column (typed or untyped) no longer runs a comparator per pair of rows. Each row gets an integer key and a radix sort orders the keys; the result is identical to the comparator sort, including empty cells last, ties in data order, and locale-aware text order. A custom `sortCompare`, a cell type with its own `compare`, and values that the comparator treats as unordered (NaN, text in a number column) still use the comparator sort. Measured with `scripts/bench-sort.mjs` on a Windows desktop (Node 24, paired runs, median of 5, 2026-11-04): sorting 1,000,000 rows by a number column with 100 distinct values takes 52 ms instead of 383 ms, by an integer column with 1,000 distinct values 54 ms instead of 735 ms, by a column of random decimals 62 ms instead of 1.9 s, and by a text column of 25 distinct names 50 ms instead of 576 ms. A text column of mostly unique strings sorts 2.9x faster (1.2 s instead of 3.5 s).
- **Faster live updates into a sorted view.** `updateCells` with `reorder: "immediate"` keeps the order array when no patched row changes place, merges large batches in one pass, and skips the view work when a patch cannot change a sort or filter value. A 100-row batch into a 1,000,000-row sorted view measures about 23 ms instead of 104 ms.
- **Faster single edits into a sorted view.** A `reorder: "immediate"` edit that moves one row shifts the order array with a plain loop instead of `copyWithin`. Measured with the `.crew/perf` harness (`h.mjs`, node level, Windows desktop, Node 24, median of 5 after 1 warmup): 500 single edits on the sort column of a 100,000-row view take 460 ms instead of 855 ms, and 100 single edits at 1,000,000 rows take 1.1 s instead of 1.75 s.
- **Faster numeric filters on number cells.** `gt`, `gte`, `lt`, `lte`, and `isBetween` compare a `number` cell value against the parsed bound without turning the number into text and back, unless the column has its own `filter.compare`. Same harness: `gte` and `isBetween` on a column of decimals over 100,000 rows take 5 ms instead of 17-25 ms, and on an integer column 5-6 ms instead of 6-8 ms.
- `onRowActionSkipped` reports `action: "moveRows"` when `reorderRows`, `moveRowsBy`, a row drag, or the move keys do nothing, with the existing reasons plus the new `reason: "view-ordered"` (an active client sort or filter owns the row order). `reorderRows` and `moveRowsBy` still return `true` or `false`. A `switch` over `action` or `reason` needs a case for the new values.
- `DataGridUrlState` and `useDataGridUrlState` take `spec` (`"sort"`, `"filter"`, `"search"`; `["sort"]` by default; `[]` turns spec sync off). Before, the sort, the filter, and the search text always went into the URL together, so a grid could not keep its sort in the URL without its filter values and search text. Use `<DataGridUrlState spec={["sort", "filter", "search"]} />` to sync all three. The legacy `join` key follows `"filter"`, and `applyFromUrl()` leaves an unlisted part alone.
- `DataGridHeaderFilter` and `BindingChips` take a `className` that merges into the trigger button and the keycap row.
- `DataGridSortIndicator` reads the grid's sort when `sortState` is omitted, so `<DataGridSortIndicator columnId="score" />` works inside a node header with no wrapper component. The rank number uses `text-xs` instead of `text-[10px]`. It also takes a `className` that merges onto its root.
- `sortCollator(locale?)` takes an optional locale, for code that sorts after an `await`.
- `filter.matchCase` on a column or a cell type makes the text and set operators and the header filter list respect letter case. `createFilterMatcher` takes `matchCase`.
- After a row move, the search highlights and next and previous match stay on their records.
- `DataGridUrlState` and saved views check the `isAnyOf` and `isNoneOf` values of a column with `choices` in client filter mode. A value stays when it matches a choice or a loaded data value of the column, without regard to case, so every value the header filter offers restores. Other values drop, and a list left empty drops its filter; a development build warns once per column. In server filter mode, or before the data loads, every value stays, and the server checks the values it receives.

## Server and data modes

- `useDataGridServerRows` warns in development when an `onSave` on `DataGridProvider` replaced the hook's (the refresh policy is off) and when an `onDataChange` on `DataGridProvider` replaced the hook's merge.
- `useDataGridPager({ pageSizeOptions })` returns `{ pager }` for a grid that pages its view.
- `DataGridProvider` pages its view with `pageSize` (or `defaultPageSize`), `page` (or `defaultPage`), `onPageChange`, and `onPageSizeChange`, and `actions.setPage` and `actions.setPageSize` change it. The grid keeps all of `data`: a sort, a filter, a pinned totals band, `exportGrid`, a streamed patch, and the `announceResults` count cover every row, and a filter change goes back to page 1. `useDataGridPager()` returns the pager from the grid, and `<DataGridPaginationBar />` with no props reads it. The bar takes every field of a pager or none: a partial set, such as `page` without its handlers, does not type-check, so spread a whole `pager`.
- `useDataGridServerRows` takes `onSave` and `refreshAfterSave`. `gridProps.onSave` runs your handler and refreshes by the policy: `"settled"` (default, once after every save in flight, or after 10 seconds), `"each"`, `false`, or a function of the saved, rejected, and failed counts. A sequential source skips the refresh while the rendered rows plus `overscan` end beyond 10 blocks. `refresh()` stays available.
- Scroll mode of `useDataGridServerRows` takes `source: "random" | "sequential"` to fix the fetch order instead of leaving it to the shape of the first answer. A random source that answers without `totalRowCount` warns in development.
- `isPlaceholderRowId(id)` (from `data-grid`) tells the placeholder id of an unloaded row from a real id, and `api.getViewRowIds({ loaded: true })` lists the loaded rows only, so no caller matches an id prefix.
- `getRowId` is optional in `useDataGridServerRows` (both modes). It defaults to the row's `id` field, the same default as `DataGridProvider`, so the hook and the grid agree; a row without a string or number `id` throws.
- `totalRowCount` makes `sortMode` and `filterMode` default to `"server"`: a window of a result cannot be sorted or filtered locally without being wrong. Set `sortMode="client"` or `filterMode="client"` to sort or filter the window in the browser. A grid without `totalRowCount` keeps the `"client"` default.
- `parseServerSpec(body, { columns, limits })` in `data-grid-server` turns an untrusted request body into a bounded, typed `ServerSpec` or throws a `ServerSpecError` with the path of the bad part. It checks column ids, per-column operators and value shapes, tree depth, group and row counts, and value lengths. The defaults accept what URL state and saved views restore (64 sorts, 500 characters of search text). The ORM recipes call it instead of a hand-written check.
- The spec types `ServerSpec` and `serverSpecKey` import from `@/components/data-grid/data-grid`. `ServerSpec` carries `searchText`, and the `fetchFilterValues` context field for the typed text is `query`.
- Under `sortMode="server"` or `filterMode="server"`, a push (`updateCells`, `updateRows`) that changes a column the spec reads keeps the row in place, marks it with `data-row-stale`, and sets `viewStale`. The mark leaves when the data delivers a new row object for the id, when the id leaves `data`, or when the spec changes. `reconcileView()` asks `useDataGridServerRows` to refetch and keeps the marks until the rows arrive; without the hook it clears them. `reorder: "immediate"` asks for the refetch on the next frame.
- `useDataGridServerRows` takes `reshapeDelayMs` (milliseconds, at least 250, off by default) and returns `reshape()`. A stale row starts one throttled `refresh()` after the delay. A push delete and `reshape()` refresh on the next frame, or after the delay when it is set. A sequential source skips that refresh while the rendered rows plus `overscan` end beyond 10 blocks.
- `deleteRows(ids, { source: "stream" })` deletes rows that the server removed. It skips `onBeforeDeleteRows`, `onSave`, and the undo history, and unchecks the rows; a range collapses onto the cursor, and the cursor clears when its row is deleted. It takes at most 100,000 ids; the rest are skipped, and development builds warn once per grid.
- `useDataGridServerRows` keeps a push made while a request is open: the cells that the push wrote stay on the row that the answer delivers.
- `useDataGridServerRows({ mode: "scroll" })` fetches the rows a grid scrolls into. The first request is block 0, the answer carries `totalRowCount`, and the hook sizes `data` from it, fetches `blockSize` blocks (default 50) around the rendered rows plus `overscan` (default 30), writes the blocks that land in one frame with one update of `data`, keeps a failed block unloaded, and shows the error bar with a Retry button that repeats the failed blocks only. `refresh()` fetches the rendered blocks again in place. It returns `unloadedCount`, `getLoadedRanges()`, and `evict(range)`. A changed count or spec starts the blocks over. In development the grid warns once when a client sort or filter changes while `data` holds unloaded rows.
- Scroll mode of `useDataGridServerRows` loads a source with no count in order. A first answer with `nextCursor`, or with neither `totalRowCount` nor `nextCursor`, makes the source sequential: the request carries the `cursor` of the block before, the grid shows the loaded rows plus one block of skeleton rows, and the next block starts when the rendered rows come within `overscan` of the end. `nextCursor: null`, `hasMore: false`, an empty block, a cursor that repeats the one just sent, and a cursor the chain returned before (compared by content, for up to 10,000 cursors) end the source (a repeat warns in development); the chain stops at 10,000,000 rows. A first answer with `totalRowCount` and no cursor stays random access. `refresh()` of both scroll engines keeps the rows on screen until the answers land, and it skips rows with a pending save and the row under an edit, drops the answer's copy of a row with a pending delete, and keeps a pending insert in its own slot when no answer row sits there (a counted source refreshes when no pending insert or delete is left); `gridProps` carries a `plugins` entry that gives the hook that read access, so put your own plugins after it. The open-ended demo uses it.
- Scroll mode aborts a block request when its rows leave the rendered rows by more than `overscan` plus one block, and runs at most `maxConcurrentFetches` requests (default 3, at most 16). A failed block that leaves the same range stops counting as an error. The blocks of `refresh()` and `retry()` wait in a queue behind the cap and count as `loading`.
- `evict()` aborts the requests it covers and keeps rows with an open edit, a pending save, or an unsaved change, and the row under the active cell. An in-flight request that started before the evict no longer lands.
- `useDataGridServerRows` takes `initialAnswer` in pages mode and shows it without a request. A finite `maxLoadedRows` bounds a sequential source: its cursor chain ends once that many rows loaded, with one development warning.
- Pages mode loads the page again when the last pending insert or delete settles, also with `refreshAfterSave: false`.
- An `onDataChange` prop after `{...server.gridProps}` runs next to the hook's merge instead of replacing it. An `onRenderedRowsChange` prop after the spread warns once in development.
- A development build warns once per grid when a sort or filter change lands on a server-mode part that no `onSortChange` or `onFilterChange` handles.
- A move from undo, redo, rollback, or `commitChange` carries `beforeRowId` and `afterRowId` too.
- `revalidateIntervalMs` refreshes the rows on a timer while the page is visible, in pages mode and in scroll mode. The value is at least 1000 milliseconds. A tick waits for a request in flight, and every refresh restarts the clock. A sequential source skips a tick while the rendered rows plus `overscan` end beyond 10 blocks.
- `prefetchNextPage` loads the next page in the background in pages mode. The pager shows it with no request and no loading state. A failed prefetch is silent, and a refresh, a spec or page size change, a local insert, delete, or move, or the start of a save drops it.
- New registry item `data-grid-server` with the hook `useDataGridServerRows({ getRowId?, fetchRows, mode?, ... })`. One hook serves a paged grid (`mode: "pages"`, the default) and a scrolling grid (`mode: "scroll"`, described in the entries below). It owns the sort, filter, search, page, and page size of a server grid unless you control them with the `spec`/`onSpecChange`, `page`/`onPageChange`, and `pageSize`/`onPageSizeChange` pairs, so a `useDataGridUrlPagination()` result spreads in. `fetchRows` receives `{ spec, start, end, cursor, signal }` (pages mode adds `page` and `pageSize`, and derives `start` and `end` from them; `cursor` is set once a page answer returned `nextCursor`) and resolves `{ rows, totalRowCount?, hasMore?, nextCursor? }`. Every answer is checked: `rows` must be an array and is cut to `end - start`, and `totalRowCount` must be a non-negative integer and clamps to 10,000,000. The hook aborts a request that a newer state replaces, goes back to page 1 when the spec or the page size changes (also when you change a controlled `spec`), keeps the last good rows on screen, and issues one request for a spec that `DataGridUrlState` restores. It returns `{ gridProps, providerProps, rootProps, spec, totalRowCount, pager, status, loading, error, retry, refresh }`, with stable callbacks. `retry()` repeats the failed request and `refresh()` fetches again and keeps the rows on screen; a row with a pending save or an open edit keeps its value through a refresh, a row with a pending delete stays gone, a pending insert keeps its own slot when it is free, through the guard in `gridProps.plugins` (put your own plugins after `...gridProps.plugins`). Options `onError`, `onLoaded`, and `onDataChange` take your handlers; a spread override of `onDataChange` drops the merge. `gridProps` spreads onto `DataGrid` (the controlled sort, filter, and search pairs, `sortMode="server"`, `filterMode="server"`, `totalRowCount`, `loading`, `error`, `onRetry`); `providerProps` and `rootProps` split it for a composed layout. The `data-grid-server-side-demo` example uses it and needs no TanStack Query or bridge component. Docs: the "Server rows example" page is built around the hook.
- `useDataGridServerRows` pages mode follows a cursor chain. A pages request carries `cursor`, and an answer with `nextCursor` makes the source a cursor source: the hook stores the cursors of the pages it reached, reuses them for back, forward, `refresh()`, and `retry()`, drops the chain when the sort, filter, search text, or page size changes, and shows a pager without a count or last page. A `page` beyond the known chain moves back to the furthest known page. New demos `data-grid-cursor-react-query-demo` (`useInfiniteQuery`) and `data-grid-cursor-swr-demo` (`useSWRInfinite`) show infinite scroll and a pager over a cursor API; `data-grid-open-ended-demo` no longer keeps the chain by hand.
- `DataGridRoot` has an error state: the props `error`, `onRetry`, and `errorState` (a node, or a function receiving `{ error, retry }`). With zero rows it shows `labels.grid.errorState` with a solid Retry button (`labels.grid.errorRetry`), with rows a slim alert bar under the header; the rows stay visible. The error value is never rendered.
- Under `filterMode="server"` with an active filter or search, an empty server answer shows the `"filtered"` empty-state reason instead of `"no-data"`. With `announceResults`, a change of `totalRowCount` after a gesture announces the server row count.
- Save acknowledgement. The new prop `onSave(change)` sends a change to a server and may return a promise: it resolves with nothing (accepted) or `{ rejected: [{ rowId, columnId?, message?, current? }] }` (the named rows or cells are refused), or rejects (the whole change is refused). `onDataChange` carries every change of `data` exactly once, rollbacks included. A push with `source: "stream"` (`updateCells`, `updateRows`) holds a patch for a row whose save is in flight (verdict reason `"saving"`) and applies it once the save settles; a later push to the same cell replaces it. An answer with more than 10,000 rejections refuses every row of its change, with one development warning. `onSave` runs after `onDataChange` for every `source` except `"rollback"` and `"stream"`; undo and redo (`"history"`) reach it. While the promise is pending, the row element carries `data-save-status="saving"`; the hooks `useDataGridRowSaveStatus(rowId)` and `useDataGridPendingSaveCount()` and the state `saveStatus` read it. A refusal reverts only the refused entries as one `onDataChange` call with `source: "rollback"` and the new field `DataChange.reverts`, clears their cell errors, marks the rows `failed` (until the next write to the row or `actions.clearSaveStatus()`), and calls the new prop `onSaveRejected({ change, rejected, error })` (`error` is the rejection reason of the promise, `null` when it resolved with `{ rejected }`). `current` puts the row as the server holds it in place of the refused row (a refused delete restores it, a refused insert removes the row) unless a newer write to the row is pending. A newer write to the same cell supersedes the earlier verdict. `useDataGridHistory` drops the history entry of a reverted change. New types: `SaveAck`, `SaveRejection`, `SaveRejectedContext`, `RowSaveStatus`. Docs: an "Acknowledge each change" section on the "Handle refused saves" page, and the live demo `data-grid-write-ack-demo` on the "Undo with server data" page.
- Save conflicts. The provider prop `resolveSaveConflict({ rowId, mine, theirs, change, message, signal })` decides what a refused row becomes when the server sent its current row. Return `"theirs"` (or nothing) to take the server's row, `"mine"` to keep the row in the grid, or `{ row }` for a merged row. `"mine"` and `{ row }` commit one change with the new `source: "merge"` on top of the server's row. `onSave` receives it and history does not record it. A promise keeps the row `saving` until it settles, and `signal` aborts when a newer write to the row starts or the grid unmounts. A change that took server content has the new field `DataChange.serverRowIds`, and `data-grid-history` drops older undo steps for those rows.
- Server-assigned ids. `actions.replaceRowId(oldId, row)` swaps the id of a row for the id of the server's row. The row keeps its data position and its view position. One `onDataChange` call fires with the new `source: "id-swap"`. `onSave` does not receive it and history does not record it. The open edit, cell errors, checked rows that a filter hides, the save status, saves in flight, and undo steps follow the new id. Flashes of the row end, and `validateRow` runs again for the swapped row. `actions.replaceRowIds(swaps)` swaps many rows in one write and one `onDataChange`; use it after a batch create.
- A row with a save in flight carries `aria-busy="true"`. A refused save is announced through the live region (`labels.grid.saveRejected`, for example "2 rows not saved"). A row with `data-save-status="saving"` is muted, and a row with `"failed"` has a tinted background. Both use theme tokens, and `getRowClassName` or CSS on `[data-save-status]` overrides them. An undo or redo over rows that are not loaded or no longer exist is not applied, and the live region reads `labels.grid.historyRowsNotLoaded` or `labels.grid.historyRowsGone`.
- `useDataGridHistory({ onSkip })` reports an undo or redo that applies nothing because a row is missing. `onSkip({ direction, reason, rowIds })` fires with `"rows-not-loaded"` (the rows are holes in a sparse `data` array; the entry stays, so the same undo works after the rows load) or `"rows-gone"` (the rows left a dense `data` array; the entry is dropped). Before, such an undo did nothing and gave no sign.
- An undo or redo that `onSave` refuses puts its entry back. A refused undo is on the undo stack again, and a refused redo is on the redo stack again.
- History follows server answers. A change with `serverRowIds` removes the older operations on those rows, an entry without operations goes, and `actions.replaceRowId` rewrites the older entries to the new id. A `datasetKey` change still clears both stacks without calling `onSkip`.
- `useDataGridServerAggregate` and `DataGridServerAggregateReporter` take `refreshAfterSave` (`"settled"` by default, `false` to opt out) and fetch again once the pending saves settle, like the pinned band. Before, only `serverAggregateRow` did, and a reporter user called `refresh()` after each save. That call can go; `refresh()` stays for manual use.
- A development build warns once per grid when a write reaches controlled `data` and neither `onDataChange` nor `onSave` is set, because the grid drops the edit on the next render. No behavior change. The `status-bar`, `url-state`, `views`, and `detail-panel` demos seed with `defaultData`, and the `loading` and `server-selection` demos set `readOnly`.
- `pageSize` and `defaultPageSize` accept `null` (every row), and `onPageSizeChange` receives `number | null`. Before, `setPageSize(null)` did nothing while `pageSize` was controlled and fired no callback. A handler typed `(pageSize: number) => void` widens to `number | null`. `useDataGridUrlPagination` maps `null` to `defaultPageSize`.
- `aggregateRow(specs, { cells?, scope? })` and `serverAggregateRow({ fetchAggregates, cells?, refreshAfterSave? })` declare a totals row in `topRows` or `bottomRows` of `useDataGridPinnedRows`. The band computes the values inside the grid and reads them by column id, so a totals row needs no state, no reporter, no memoized band array, and no `accessorKey` that equals the column id. `useDataGridPinnedRows` compares `topRows` and `bottomRows` by entry identity, so an inline array of stable entries keeps the plugin. `serverAggregateRow` sets the band `status` and fetches again after the pending saves settle. The old wiring with `DataGridAggregateReporter` and `DataGridServerAggregateReporter` still works.
- The `move` operation of a change carries `beforeRowId` and `afterRowId`, so a server can place the moved row.
- `useDataGridServerRows({ plugins })` mounts your plugins after the refresh guard, and the scroll option `onRenderedRowsChange` runs after the handler of the hook. `server.gridProps` sets `headerClickBehavior: "sort"`. In pages mode, a development warning fires when the result has more than one page and nothing reads `server.pager`.

## Import and export

- `Dropzone` has an `accessibleDescription` prop that replaces the screen reader text, and `DataGridImportDialog` sets it from the new `labels.io.dropzoneDescription(types, maxSize)`, which takes the accepted extensions as a list and the size limit as text. The text was fixed English.
- The import dialog delimiter menu offers pipe (`|`), and `CsvDelimiter` includes `"|"`. The `labels.io` object has a `delimiterPipe` label. Detection guesses only comma, semicolon, tab, and pipe.
- A paged grid exports and totals every page by default; `scope: "page"` on `exportGrid`, `printGrid`, and `useDataGridAggregate` limits them to the shown page, and `actions.setPageSize(null)` turns paging off for an uncontrolled page size. A filter set through props reports `onPageChange(1)`.
- `exportGrid` and `DataGridExportButton` take a `source` that returns the rows of the whole server result: an array, or an async iterable of batches. The source receives the grid's `spec` and an `AbortSignal`. `maxRows` (default 1,000,000), `maxBytes` (default 256 MiB), `signal`, and `onProgress` bound and observe the export. A negative limit counts as 0, and `NaN` reads as the default. `exportGrid` resolves `{ rowCount, truncated }`. With a `source`, the button menu adds "Export all rows" items and a "Cancel export" item. New labels: `io.exportAllXlsx`, `io.exportAllCsv`, `io.exportCancel`, `io.exportCancelled`, `io.exportFailed`, `io.exportDone`.
- Export options `output`, `columns`, and `formatCell`, for loaded rows and for a `source`. `output` receives the finished `Blob` instead of the browser download, so a report can go to your server. `columns` lists the column ids to write, in order, hidden columns included. `formatCell` returns a string, number, boolean, `Date`, or `null` per cell; XLSX writes numbers, booleans, and dates as typed cells, and a string is always a text cell. A string that `formatCell` returns is cut at 32,767 characters, CSV text still gets the formula quote prefix, and `maxRows` and `maxBytes` count the formatted output. A loaded export with `output` shows the button as busy while it runs. `ExportSourceContext.columnIds` names the columns of a `source` export. `exportRows` (the engine of a `source` export) is exported for custom formats.
- Import pipeline hooks on `DataGridImportButton`, `DataGridImportDialog`, and `useDataGridImportPreview`: `parseFile` replaces the built-in parser, `accept` sets the drop zone's file types, `csvEncoding` decodes a CSV from a fixed list of `TextDecoder` labels (`IMPORT_CSV_ENCODINGS`), `importDefaults.defaultHeaderRow` takes the 0-based index of the header row and drops the rows above it, `processImportRows` rewrites or drops the data rows (`false` cancels), and `processCellFromText` parses each cell. Without it, an import now uses the grid's `processCellFromClipboard` when the grid sets one, then `fromText`, so a grid with that prop parses imported cells through it, on the asynchronous chunked path (its value still goes through `validate`). Every hook result is checked against `importLimits` after the hook runs. `onImport` gets `{ signal, rejected, fileName, sheetName, mapping }`, and `ImportRejectedCell.message` carries the validator's reason. `onImportError` receives a rejected `onImport`, and the dialog shows `labels.io.importFailedWithMessage` when the error has a message. `DataGridImportDialog` takes a `file` to load on open, and `useDataGridImportPreview().build()` runs the row hook and the row build. `DataGridImportButton` takes every prop of the dialog except `open` and `onOpenChange`. New labels: `io.importFailedWithMessage`, `io.importBuildFailed`.
- `Dropzone` accepts `aria-labelledby`, which names the drop surface instead of `aria-label`.
- The import dialog's default append (no `onImport`) refuses on a `readOnly` grid and shows the import failure message, like the `totalRowCount` refusal. Redo and undo of a bulk write on a `validationMode: "warn"` column keep its flags.
- A node `header` without `headerText` names its column by the plain text of its elements (`<span><User /> Name</span>` reads `Name`) for screen readers, menus, export, import matching, and autosize. Before, the column id named it. A component inside the node adds no text, so set `headerText` for those; `headerText` still wins.
- `onImport` of `DataGridImportButton` and `DataGridImportDialog` is optional. Without it, a confirm appends the rows to `data` as one undoable change with `source: "import"`, which reaches `onDataChange`, `onSave`, and `validateRow`. A grid with `totalRowCount` has no default: a confirm writes nothing, the dialog shows `labels.io.importMergeFailed`, and a development build warns once. A passed `onImport` replaces the default. The shortest import is now `<DataGridImportButton createRow={createRow} />`.
- `DataGridImportDialog` takes a `className` that merges into the dialog content, so a wide mapping table can widen the dialog. `DataGridImportButton` keeps its `className` on the button.
- `processCellForClipboard` gets `ctx.text` (the cell type's copy text), and `processCellFromClipboard` and the import `processCellFromText` get `ctx.fromText` (the column's own parser). Return them for the cells you do not change: `(value, { column, text }) => (column.id === "price" ? "$" + value : text)`. The new `ClipboardCopyCtx` and `ClipboardPasteCtx` types describe the contexts.
- `useDataGridImportPreview()` needs no argument: `build()` reads `columns` and `cellTypes` from the grid, and options with the same names override them. `printGrid` takes `direction`. New labels: `labels.io.importNeedsOnImport`, `importReadOnly`, and `emptyDropzoneCaption`.
- The import button is disabled, with the reason, for a server grid without `onImport` (also with a `totalRowCount` of `null`) and for a `readOnly` grid. A custom `parseFile` can return a `"|"` delimiter. `accept={{}}` reads "All file types accepted". `csvEncoding` is typed.

## Accessibility and keyboard

- The `?` key of `useDataGridKeybindings` leaves a `?` typed into an input, textarea, select, or contenteditable that a cell or header renders to that field, and ignores `?` during an IME composition. It took the key and opened the dialog instead.
- The live region reads `labels.grid.viewStale` once when the view turns stale, at most once every 30 seconds, in every data mode.
- With `announceResults`, the end of a load (`loading` true to false on `DataGridRoot`) is announced when the server-evaluated filters, sort, search, or `totalRowCount` changed since the last load ended, or when the load before it failed: the `totalRowCount` or the loaded rows, "No results" for none. A block fill or page change with the same spec and count stays quiet, and a failed load stays with the `role="alert"` error bar. The live region keeps its 500 ms trailing pause, so a run of refreshes is read once.
- `api.runShortcut(action)` runs what the key bound to a keymap action runs: the `commands` entry with its `when` and `scope`, else the built-in with its guards. An unbound action still runs. A toolbar button is `onClick={() => api.runShortcut("deleteRows")}`, with no target computation. `DataGridGlobalShortcuts` and the context menu fill items use it.
- `DataGrid` and `DataGridRoot` take `aria-label` and `aria-labelledby`, which name the `role="grid"` element: `<DataGrid aria-label="Tasks" />`.
- A keymap binding with a punctuation key and no `shift`, such as `mod+/` or `?`, matches with or without Shift on any layout. Before, only a bare punctuation key (`?`) ignored Shift, and `mod+?` needed `mod+shift+?`. A binding that names `shift` still requires it.
- A plugin `keymap` binds the plugin's own commands, not only the six pluggable actions. A key that another action already holds stays with that action (the first owner wins, dev-warned). The consumer `keymap` still wins and `[]` unbinds.
- `keymap` accepts the names of custom commands without a cast.
- Keymap actions `moveColumnTowardStart`, `moveColumnTowardEnd`, `widenColumn`, and `narrowColumn` move and resize the column of the focused header, else of the active cell, in steps of 16 px. They have no default keys, because each free chord collides with a browser, OS, or screen reader binding; the header menu holds the same commands.
- A grid without an accessible name warns once in development.

- Fix: a `keymap` binding with an unknown modifier, such as `"Mod+Z"` (modifiers are lowercase), never matches. It matched the bare key, so a bare <kbd>z</kbd> on the active cell ran undo. The development warning stays.
